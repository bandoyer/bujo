# Slice 1.5.1 — the page model and its pages

Status: **operator review hold; do not start the swarm yet.**

This is the first stage of the source-faithful realignment governed
by `docs/METHOD.md`, `PLAN.md`, and ARCHITECTURE.md, in that order.
Every journal entry has exactly one page residency. Dates describe an
entry; they never make it appear on another page. A temporary review,
Index, or later search lens may reference the original entry without
becoming another page or changing where it lives.

This slice touches the schema — the first time since 1.2 — so the
`bujo-conventions` invariants apply everywhere they are not explicitly
revised below. **The rulings are pre-decided. Report a conflict rather
than inventing a different method.**

## Acceptance contract

- One append-only migration introduces the page model. Do not edit a
  landed migration.
- Page placement is set at creation and immutable through public
  application/domain APIs. Movement always appends a successor.
- Root bullet kinds, page dates, and ordinary write affordances obey
  the page matrix and temporal boundaries below.
- Every log scope is a residency query. `occurs_on` never grants
  membership in a Daily, Monthly, or Future page.
- All time-dependent decisions receive a caller-provided `as_of` date,
  distinct from the parser's page-relative `today` context.
  `Entry` must not read the system clock.
- Existing overdue residents stay visible. Time passing never moves,
  hides, repairs, or invalidates an entry.

## Schema — one migration

- Add `page_kind`, a NOT NULL string with allowed values
  `daily | monthly_calendar | monthly_tasks | future | collection`.
  For each existing tree, the root is the placement authority: a root
  with `collection_id` already carries explicit Collection placement,
  so backfill that whole tree as `collection`; otherwise backfill the
  whole tree as `daily` on the root's `logged_on`. Normalize every
  descendant to the root's placement — legacy children were allowed to
  carry unrelated dates/Collection ids even though rendering already
  treated them as part of the root. Leave no long-lived database
  default that could silently place future rows.
- Rename `logged_on` to nullable `page_on`. Preserve the root's date for
  each Daily tree and clear it for each Collection tree. Thereafter its
  shape is the day for a Daily Log, the first day of the month for
  either Monthly page, and NULL for Future Log or Custom Collection
  residency.
- `collection_id` is placement and is present exactly for
  `page_kind: "collection"`. It belongs to the same user as the entry.
- `occurs_on` keeps one meaning: the date an entry is *about*. It is
  required for Monthly Calendar and Future Log roots; a Calendar date
  must fall within `page_on`'s month. It is never placement.
- No other schema shape changes. The placement backfill may set or
  clear a descendant's `collection_id` to match its root as ruled
  above; content and lifecycle data do not change. Task state remains
  exactly `open | done | struck | migrated`; events and notes keep NULL
  state; soft deletion, UUIDv7 ids, the unique successor index, and
  dormant sync columns retain their contracts.
- The existing 1.4.1 Future month-add rows backfill as Daily residents.
  Do not guess at them in a data migration. The operator will inspect
  and deliberately repair the few production rows after deploy.
- This is honestly an irreversible data migration. Once
  Future/Collection residents have NULL `page_on`, the old
  `logged_on NOT NULL` shape cannot be restored without inventing
  dates. Declare that irreversibility in the normal Rails way; do not
  provide a nominal rollback that fabricates residency or fails only
  after touching real data.

## Structural page grammar

The compatibility rule applies to root entries. A nested child may be
any bullet kind as supporting context, but it must share its parent's
entire placement (`page_kind`, `page_on`, and `collection_id`).

| Page kind | `page_on` | Allowed root kinds | `occurs_on` |
|---|---|---|---|
| `daily` | exact day | task, event, note | optional |
| `monthly_calendar` | first of month | task, event | required; inside that month |
| `monthly_tasks` | first of month | task | optional |
| `future` | NULL | task, event | required |
| `collection` | NULL | task, event, note | optional |

Model validation owns this structural matrix. A root note on the
Future Log, a root event on Monthly Tasks, a Calendar entry outside its
month, a cross-page child, or a foreign user's Collection is invalid.

## Temporal admission — domain boundary, not row validity

Rows do not become invalid as the calendar advances. Capture and
movement commands evaluate these rules against their explicit `as_of:`
argument:

- **Daily Log:** ordinary capture accepts today or a past day. Future
  Daily pages render any residents already there but have no capture
  affordance and refuse a crafted write request. Ryder permits setting
  up tomorrow's Daily Log the night before; v1 consciously defers that
  clock-dependent exception rather than inventing a cutoff.
- **Monthly Calendar and Tasks:** ordinary direct capture accepts the
  current or a past month. A future Monthly page can render a successor
  deliberately carried there, but has no ordinary capture surface and
  refuses a crafted direct write. Monthly setup/migration will create
  those future residents through explicit setup and movement paths in
  slice 1.5.3.
- **Future Log:** a new root must be dated strictly after the end of
  `as_of`'s month. "Tomorrow" is not enough when tomorrow is still in
  the current month; that plan belongs on the current Monthly Calendar.
  Occupied current and overdue Future groups remain rendered until a
  hand acts, but their add affordance is absent and direct writes are
  refused.

`Entry.capture!` gains explicit placement and an injected `as_of:` for
admission while retaining `today:` as the parser's page context. Daily
and Calendar-row capture use that row's date as parser `today`; Future
month-add uses its composed date; Monthly Tasks uses `as_of` because the
page has no day row. The application/domain command validates temporal
admission before creation. A timeless Active Record validation must not
call `Date.current` or make an old Future resident invalid merely
because its month arrived.

For the web path, the controller snapshots `Time.zone.today` once per
request and passes it as `as_of`; forms do not supply or override that
value. Tests inject the command date directly or through time travel.

## Placement immutability

`page_kind`, `page_on`, and `collection_id` are creation-only placement
through supported application/model APIs. Normal assignment, update,
mass assignment, lifecycle actions, and sync-facing domain operations
must fail loudly when they attempt to change placement on a persisted
entry, and a re-read must show the original values. A silent
`attr_readonly`-style success is insufficient because the caller would
believe a move happened. A deliberate move creates a successor on the
destination page.

This is not a claim that arbitrary SQL cannot alter a SQLite row. Do
not add triggers solely to pretend otherwise, and do not make raw-SQL
placement attacks an acceptance bar. Database constraints continue to
defend structural facts they can express; the unique index on
`migrated_from_id` remains the final guard against two successors.

## Residency scopes and rendering

- `daily_log(date)` returns only `page_kind: daily, page_on: date`.
- `monthly_calendar(month)` and `monthly_tasks(month)` return only
  their respective page kind and first-of-month `page_on`. Calendar
  roots order by `occurs_on`, then capture; Tasks stay in capture order.
- `future_log` returns only Future residents in calendar/capture order.
  The screen renders every occupied month group, including current,
  overdue, and later-than-runway groups. The empty add runway still
  begins after the current month.
- Child rendering follows its resident root as today. `open_tasks` and
  unrelated orderings keep their contracts.
- A Daily entry may carry a future `occurs_on`; it still appears only
  on its Daily page. A Future or Calendar resident never materializes
  on its date's Daily page. Time passing changes no scope result except
  which direct-write controls are offered.

## Append-only movement

Replace the old date-shaped migration API with one destination-page
operation. It preserves the existing copied-entry contract and creates
one successor with `migrated_from_id` pointing at the predecessor.

- The destination must satisfy the structural page grammar and the
  command's temporal admission rule.
- An open task predecessor becomes `migrated`. Done, struck, or already
  migrated tasks refuse with the existing `LifecycleError` contract.
- Event and note predecessors retain exactly NULL state; their moved
  status is the existence of a successor. A task successor is `open`;
  an event/note successor also carries exactly NULL state. Any second
  move raises `LifecycleError` before insertion, and the unique
  successor index backs the domain check rather than becoming the
  user-facing `RecordNotUnique` failure.
- The backend operation remains kind-general so later migration can
  carry notes into Custom Collections. Outbound gestures in *this*
  slice are deliberately narrower: an eligible task on a Daily or
  Monthly page may `Migrate` to the Tasks page for the month after its
  source page; an eligible task/event there may `Schedule…` after the
  current month. Future residents get their guided outbound actions in
  1.5.3. A note does not gain a Future Log action.
- Glyph direction derives from the successor's residency: `<` when the
  successor is on the Future Log, `>` for a Monthly or Custom page.
  It no longer derives from `occurs_on`.
- No movement is implicit, scheduled, bulk, or caused by reading a
  page. Chain length remains visible history, not metadata to collapse.

## Page gestures — app layer

### Daily Log

- Today and past pages keep the hidden write-on-page bar and may root
  task, event, or note bullets. A future page renders residents and
  navigation only; it does not render the reveal target or bar.
- Existing Daily behavior remains intact: parser forms, priority,
  tags, nesting, counts, collapsed task actions, themes, and hands.
- `Migrate` on an eligible task writes its successor to the Tasks page
  for the month after the Daily page being reviewed and renders `>` on
  the predecessor. The destination follows page context, not the wall
  clock.
- `Schedule…` is offered for eligible tasks and events, never notes.
  It accepts only a date after the current month, writes a Future Log
  successor, and renders `<`. Same-month and past dates take the normal
  rejected-action path; nothing is silently corrected or rerouted.

### Monthly Calendar

- Each date row is a deliberate Calendar writing surface for current
  or past months. It places a task or event root on the Calendar page
  with `occurs_on` equal to that row; note controls are absent and a
  crafted note request is refused.
- The date's Daily Log remains a separate, clearly labelled tap target
  (all interactive targets at least 44px). Calendar rows render only
  Calendar residents; the linked Daily page may be empty. The resident
  entry itself renders in place rather than masquerading as a link to
  that Daily page; eligible task/event actions follow the movement
  rules above.
- Future Calendar pages render residents but are capture-closed. No
  ordinary add control appears there.

### Monthly Tasks

- Current and past Tasks pages use the hidden write-on-page gesture but
  create task roots only. The server refuses crafted event/note roots.
- The page renders only its residents. `N open · M logged` counts this
  curated page, not all tasks whose dates happen to fall in the month.
- A resident renders and takes its normal task lifecycle/actions in
  place; it is not a link to an unrelated Daily page.
- Future Tasks pages render deliberately migrated residents but are
  capture-closed.

### Future Log

- Month-add writes a Future resident with composed `occurs_on` and NULL
  `page_on`. It supports task and explicit event glyphs; a note glyph is
  structurally refused. Parser behavior otherwise remains frozen.
- Add controls appear only on months after the current month and the
  server enforces the same boundary. Invalid calendar days, current or
  past months, and disallowed kinds use the existing refusal path.
- Every occupied month remains visible even after it becomes current or
  overdue. A resident renders in place, not as a link to its eventual
  date's Daily page. Nothing leaves the queue or appears elsewhere
  until a hand moves it; guided scan-out belongs to 1.5.3.

## File scope

`db/migrate/`, `db/schema.rb`, `app/models/`, `app/controllers/`,
`app/views/`, `app/assets/stylesheets/`, `app/javascript/`, and `test/`.
NOTHING in `lib/` or `Gemfile`. The parser is untouched and its mutation bar
must not move. `config/` is allowed only if an unavoidable route change
requires it (none is expected).

The schema follows every `bujo-conventions` invariant except the one
this slice deliberately supersedes: logs become residency scopes over
immutable page columns instead of date queries. The operator updates
the tracked skill only after the schema lands.

## Ruled browser flows

1. A future Daily page renders an existing resident but no writing
   affordance; a past Daily capture still lands on that page.
2. Current-month Calendar capture accepts a task and event, refuses a
   note, and changes neither the matching Daily page nor Tasks page.
3. Monthly Tasks capture creates a task only; its counts come solely
   from residents. A future Monthly page has no capture control.
4. A Future month-add outside the current month waits only in its
   occupied group. Current-month add is absent and a crafted request is
   refused; an overdue resident remains visible.
5. `Migrate` on a Daily task renders `>` and puts one successor on next
   month's Tasks page without granting that page direct-write controls.
6. `Schedule…` on a Daily task after the current month renders `<` and
   creates one Future successor. A same-month choice is refused.
7. A Daily event can be scheduled to the Future Log once. A Daily note
   exposes no Schedule action. Neither original changes task state.
8. A Future/Calendar entry on SEP 5 never appears on SEP 5's Daily Log
   merely because SEP 5 arrives.
9. Today's capture remains green end to end for all existing kinds,
   parser forms, priority, tags, nesting, actions, and counts.
10. Changed screens are verified with both themes and two hands, using
    the existing browser/system-test rules.

## Required tests and adversarial review

Fast lane:

- both root migration/backfill shapes (uncollected → Daily with its
  date; collected → Collection with NULL `page_on`), descendant
  normalization to the root even when legacy dates/Collection ids
  disagree, NOT NULL `page_kind`, nullable `page_on`, and absence of a
  placement default afterward;
- the complete root/child structural matrix, same-user Collection
  ownership, Calendar-month validation, and exact task-state/null-state
  semantics;
- temporal command boundaries with injected `as_of`, especially
  tomorrow-inside-current-month versus first day of next month, plus
  old Future residents remaining valid;
- domain/API and mass-assignment placement immutability on persisted
  rows, asserting both an announced failure and unchanged reloaded
  values — no raw-SQL immutability fiction;
- kind-aware movement, done/struck/already-moved refusals, one-successor
  chain enforcement (including exact `LifecycleError` and a raw-SQL
  unique-index probe), and glyph direction from the successor page;
- pure residency scopes, every occupied Future month, future Monthly
  residents, and an `occurs_on` value that never leaks across pages;
- every existing test updated to the new semantics rather than deleted,
  skipped, broadened, or weakened.

Known expectation rewrites are explicit: existing controller cases that
use a future Daily date merely to exercise the `on` parameter move to a
past date, while a new case owns future refusal; `logged_on` assertions
follow the column rename without losing their intent; Monthly tests
replace derived-membership expectations with residency expectations;
and all existing task-movement assertions survive alongside the new
event/note cases.

System lane covers all ten ruled browser flows, server refusal behind
every hidden/absent control, touch targets, both themes, and both hands.

## Quality bars

Run the standard battery: fast and system tests, RuboCop, coverage with
CRAP ≤ 6, jscpd, and grep-verified hand mutations. `lib/` is out of
scope, so `Bujo::RapidLog*` mutation must remain exactly 1105/1105.
Measure path scope from the accepted-spec commit, not from an arbitrary
older main commit. Prove `bin/rails db:migrate` from the prior schema
and from a fresh test database; the migration's lack of a fake down path
is deliberate.
