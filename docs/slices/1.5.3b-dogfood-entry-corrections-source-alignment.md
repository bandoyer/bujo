## Observable clarifications fixed by the landed source

These points make existing source semantics explicit for correction tests. They
do not add behavior beyond the approved contract.

1. **Canonical Edit line.** The prefilled line is, in order, optional `*`, the
   stored words, stored tags as `+tag` tokens in their stored order, an ISO
   `occurs_on` when present, and canonical 24-hour `time_of_day` when present.
   It contains no leading bullet or lifecycle glyph. Thus a done task opens as
   its words and metadata, not as `x ...`; Save preserves `done` independently
   of the parsed line.
2. **Relative-token anchor.** Correction uses the same parser-day convention as
   capture on the resident surface. Daily uses its persisted `page_on`;
   Calendar and Future use the rendered root's persisted `occurs_on`; Monthly
   Tasks and Collection use the request's one snapshotted `@today`. A nested
   row uses its rendered root's day. Canonical prefill remains ISO and therefore
   reparses identically regardless of the request date; this rule matters only
   when the reader deliberately types a relative date during Edit.
3. **Correction is not recapture.** Save applies structural validity, the
   approved kind/history locks, and the persisted page's root vocabulary. It
   does not reapply direct-capture time admission. In particular, a kept
   overdue Future live end can correct words or a structurally valid date
   without moving, disappearing, or being refused merely because its date is
   no longer beyond the current month.
4. **Canonical returns are persisted returns.** Edit and Schedule success or
   refusal return from `page_kind`, `page_on`, and kept `collection_id` on the
   command subject. `viewed_on`, `return_to`, placement, Collection, parent,
   predecessor, and destination parameters cannot select that return. Existing
   Complete, Strike, Reopen, Migrate, and Move to Collection return behavior is
   unchanged outside the corrections explicitly approved for this slice.
5. **The current month is the request month.** Schedule compares the submitted
   ISO date with the controller's single snapshotted `@today`, not with the
   source Entry's Daily or Monthly page. A later day in `@today`'s month goes to
   that month's Calendar; the first day after its month end goes to Future.
6. **One-shot Undo is not journal state.** The confirmation/offer may survive
   only the resolution redirect. Any ids or action description rendered into
   its POST are claims to revalidate, never authority. The kept, same-user
   Entry chain and target-month-derived source sets alone decide whether Undo
   writes and what exact source placement it restores.

## Source-to-contract alignment

### Monthly capture vocabulary

The two old allowlists are aligned in one change:

- `Entry::ROOT_KINDS` currently admits Task/Event on Monthly Calendar and only
  Task on Monthly Tasks. Both ordinary Monthly root rows now admit all three
  kinds.
- `_calendar.html.erb` and `_tasks.html.erb` currently pass those same narrow
  lists to the shared `_kind_buttons.html.erb`; both ordinary forms now render
  Task/Event/Note.
- `EntriesController#create`, `default_kind`, and `Entry.capture!` already
  provide the shared parser and server-derived placement. They remain the
  command boundary, so the rendered and crafted-kind matrices cannot drift.
- Monthly Migration setup continues through its separate task-only form and
  named admission context. Future remains Task/Event. Its Note exclusion is
  not widened by the ordinary Monthly ruling.

The database constrains page-kind vocabulary but has no root-kind allowlist,
so this approved vocabulary correction requires no migration or schema edit.
The approved contract intentionally outranks the older Monthly root-kind prose
in method/plan/architecture documents; pack roles do not edit those documents.

### Entry correction and command policy

The landed shared Entry row already centralizes every ordinary page in
`entries/_entry.html.erb`, `_entry_line.html.erb`, and `_task_actions.html.erb`.
Edit joins that one offered-command list and one collapsed strip:

- the conventional write is `PATCH /entries/:id` (`EntriesController#update`);
  opening and cancelling its already-rendered inline panel are browser-local
  and require no GET Edit endpoint;
- the command-policy matrix treats the routed update as the reader's `Edit`
  command, including Future and Collection residents, and continues to refuse
  every row with a successor before the action body runs;
- a live end with a predecessor and no successor may correct words/metadata but
  keeps its kind; an unresolved row with neither predecessor nor successor may
  use the approved kind conversion; and
- Future's resident wrapper must own the same transient action controller as
  the other ordinary pages so an offered Edit is actually reachable there.

The model-owned correction receives the parsed line and selected kind, locks
and reloads the kept row, checks the approved history/kind predicates, and
changes only the approved editable fields. Parser state never performs a task
transition. Presence of crafted immutable/history/ownership fields is a whole
command refusal, not a silently ignored successful edit. A refusal leaves
`updated_at` and every domain field unchanged.

The existing current-user kept lookup and unavailable-Collection lookup in
`EntriesController#set_entry` already provide the approved nondisclosing 404
boundary. The current `redirect_to_viewed_page` is parameter-driven for dated
legacy commands, so Edit and Schedule need the persisted canonical-return path
described above rather than trusting it unchanged.

No parser file or parser test changes are authorized. Application code may use
the existing parse/render vocabulary, but correction remains an Entry domain
operation rather than a second grammar or editor model.

### Scheduling and native date control

`EntriesController#schedule` currently sends every eligible Task/Event to
Future. It remains the only schedule action and continues to call append-only
movement, but derives one of the approved destinations:

- later in the current month: `monthly_calendar`, current month boundary
  `page_on`, exact submitted `occurs_on`;
- after the current month: `future`, NULL `page_on`, exact submitted
  `occurs_on`.

The persisted kind, live-end check, field copying, one-successor index, and
glyph derivation remain owned by `Entry#move_to!`. The request's date is the
only destination input. Missing/malformed/today/past dates refuse before a
write, and no crafted placement or return field changes the outcome.

The existing schedule step already uses Rails `date_field`; it needs no new
controller or dependency. Its hidden `Schedule date` label becomes visible
`Schedule for`, the date field loses its narrow maximum width, and the visible
Schedule/Cancel controls retain at least 44px targets.

### Empty writing surfaces and Collection creation

Daily and Collection currently render `Nothing logged yet.` outside the blank
capture button. On an empty writable page, that copy and its surrounding entry
region become content of, or an accessible label for, the one real `Write on
this page` button. The trailing canvas remains the same button/form ownership;
there is no nested control or generic-div click handler. A future Daily page
still renders inert copy and no capture button.

`CollectionsController#create` already persists an unindexed same-user row and
redirects to its canonical URL, but it does not set the approved notice. It is
therefore focused source scope for `Collection created.`. Because the global
layout normally places flash above `<main>`, the Collection page must defer or
locally render that notice directly below its title/context so title-first
hierarchy remains true. The empty guidance becomes exactly `Add a first entry,
then add it to the Index.`

The landed `Collection#registrable?`, explicit register action, and server-
allocated ordering already supply the post-first-entry `Add to Index` gesture.
They do not need a model change. Create, reveal, and capture remain unindexed.

### Stable row geometry and lifecycle ink

All affected ordinary rows converge on the existing shared four-column Entry
grid. Calendar's date and Future's day remain outside it; children keep only
their existing indentation. The landed defects map directly to two shared
rules:

- stop adding `entry--selected` left/right padding; selection may change only
  paint such as background, radius, border, or outline; and
- stop applying/rendering `entry--muted` for done or migrated rows. Struck text
  keeps `currentColor` and explicitly uses at least `2px` decoration thickness,
  while the glyph remains outside the struck span.

The same shared geometry applies to ordinary Edit/Schedule strips, Monthly
Migration candidates, confirmations, and Undo. No page-specific Entry grid is
authorized.

### Monthly Migration Undo

The landed controller already owns the seven ritual resolutions, live
candidate derivation, exact target-month source relations, canonical stage,
and shared `REFUSAL_ALERT`. Add one named Undo POST to that controller and one
model-owned compensating movement operation; do not create a ritual record or
generic undo/history controller.

Ordinary `Entry#move_to!` cannot by itself restore every approved source. Its
Future admission rejects a date in the current month, while Undo must restore
an exact due-Future residency even after that date becomes current or overdue.
The compensating operation therefore validates the persisted first movement
and exact original source inside one transaction without weakening ordinary
capture or Schedule's Future boundary. It appends the third row through the
same UUIDv7/unique-successor invariants and never mutates or deletes either
earlier row.

Strike Undo uses the existing reopen transition on the same still-struck task.
Both Undo shapes must lock/revalidate the complete kept same-user subject chain
and current live end before writing, so a stale tab or uniqueness race becomes
the established refusal with zero unrelated changes rather than a raw database
error.
