# Slice 1.2 — entries & collections

You are implementing bujo's data model: the `Entry` and `Collection`
records, the log queries over them, the task lifecycle (including the
append-only migration chain), and the bridge from the slice 1.1 parser
to persisted rows. No controllers, no views, no routes — the model
layer complete enough that slice 1.3 is purely UI.

Read `PLAN.md`, `ARCHITECTURE.md` (its schema section binds here), and
the project article first. **This spec pre-decides every judgment
call. The tables and rulings are the contract — do not re-litigate;
put anything you believe is missing in your final report.**

## Schema

Two tables. All ids are UUIDv7 strings (SQLite TEXT primary keys),
client-generatable — phase 2's sync protocol depends on the client
minting ids offline, and UUIDv7's time-ordering makes string sort ≈
creation order.

```
entries
  id               string PK (UUIDv7)
  user_id          string FK -> users, null: false
  kind             string, null: false        # task | event | note
  state            string, null: true         # tasks: open|done|struck|migrated · events/notes: NULL
  text             text,   null: false        # non-empty
  priority         boolean, null: false, default: false
  tags             json,   null: false, default: []   # downcased strings, parser order
  logged_on        date,   null: false        # which Daily Log it was captured into
  occurs_on        date,   null: true         # calendar placement (events, scheduled tasks)
  time_of_day      string, null: true         # "HH:MM" 24h, parser-normalized
  collection_id    string FK -> collections, null: true
  parent_id        string FK -> entries, null: true      # nesting (note under a task)
  migrated_from_id string FK -> entries, null: true, UNIQUE  # the append-only chain
  hlc              string, null: true         # dormant until phase 2
  server_seq       bigint, null: true, index  # dormant until phase 2
  deleted_at       datetime, null: true       # soft delete
  created_at / updated_at

collections
  id / user_id / hlc / server_seq / deleted_at / timestamps as above
  name             string, null: false        # unique per user among kept rows
```

Indexes on entries: `[user_id, logged_on]`, `[user_id, occurs_on]`,
`[user_id, state]`, `collection_id`, `parent_id`, and **unique** on
`migrated_from_id` — the database is the backstop that an entry is
migrated at most once, making the chain a chain and never a tree.

**Architecture refinement (already agreed):** collections have no
`kind` column. ARCHITECTURE.md sketched `kind custom|future`, but the
Future Log is a *date query* like the daily and monthly logs (entries
with a future `occurs_on`), not a container. Collections are custom
collections, full stop.

Id generation: one concern, `UuidV7Id` in `app/models/concerns/`,
included by both models: `before_create { self.id ||=
SecureRandom.uuid_v7 }`. The `||=` is the point — a caller-supplied id
(fixtures now, sync later) must survive.

## Models and rules

`Entry` validations and semantics:

- `text` present and non-blank; `kind` in task/event/note.
- `state` is **exactly** `open|done|struck|migrated` for tasks and
  **exactly NULL** for events and notes — both directions validated.
- `time_of_day` nil or matching `\A([01]\d|2[0-3]):[0-5]\d\z`.
- `parent` when present: same user, not self, any kind, any depth —
  the book nests freely; we don't police depth.
- Soft delete: **no default_scope** (a known footgun). Scope `kept` =
  `where(deleted_at: nil)`; every log query below builds on `kept`.
  `soft_delete!(at: Time.current)` sets `deleted_at`; deleting a
  parent does not cascade (children keep their own lifecycle).
- No model method may call `Date.today`/`Date.current` internally —
  every query and operation takes its date from the caller (the same
  testability rule the parser follows; `Time.current` as a keyword
  *default* is fine because tests can override it).

`Collection`: `name` present, unique among the user's kept
collections (case-insensitive), soft delete as above.

`User`: gains `has_many :entries` and `has_many :collections`.

## Logs are queries

Class-level scopes on `Entry`, every one starting from `kept` and
scoped to a user (they will be called as `user.entries.daily_log(...)`;
write them as scopes so that composes):

| Scope | Definition | Ordering |
|---|---|---|
| `daily_log(date)` | `logged_on = date`, **roots only** (`parent_id: nil`) — children render nested via `children` | `created_at` (capture order — id order ties-breaks identically thanks to UUIDv7) |
| `monthly_calendar(month)` | `occurs_on` within `month.all_month` — events *and* dated tasks, per the mocks | `occurs_on`, then `time_of_day` (nils last), then `created_at` |
| `monthly_tasks(month)` | tasks with `logged_on` within the month | `created_at` |
| `future_log(after:)` | `occurs_on > after` | `occurs_on`, then `time_of_day`, then `created_at` |
| `open_tasks` | tasks, `state = open` | `created_at` |

`month` arguments are any `Date` inside the month (`month.all_month`
does the work); `after:` is a `Date` — slice 1.4's Future Log will
pass the last day of the displayed month.

## The task lifecycle

Instance methods on `Entry`, tasks only. The state machine is small
and strict; every violation raises `Entry::LifecycleError` (a named
error class on the model — callers in 1.3 rescue it):

| Operation | Valid from | Effect |
|---|---|---|
| `complete!` | open | state → done |
| `strike!` | open | state → struck |
| `reopen!` | done, struck | state → open |
| `migrate_to!(logged_on:, collection: nil)` | open | see below |
| `schedule_to!(occurs_on:)` | open | see below |

Calling any of these on an event or a note, or from a state not
listed, raises `LifecycleError`. Idempotence is deliberately NOT
provided (`complete!` on a done task raises — the UI decides what
re-tapping means, not the model).

**Migration is append, never mutation of history.** Both migrating
operations, in a single transaction:

1. Create the successor: same user, kind, `text`, `priority`, `tags`,
   fresh id, `state: "open"`, `parent_id: nil` (children do not follow
   automatically — the ritual UI decides that later).
   - `migrate_to!` sets the successor's `logged_on` from the argument,
     `collection_id` from the argument (nil = none), and **clears
     `occurs_on`/`time_of_day`** — the task is being re-planned into a
     month or collection, not onto a calendar slot.
   - `schedule_to!` sets the successor's `occurs_on` from the
     argument, keeps `time_of_day`, sets `logged_on:` to the
     predecessor's `logged_on` (capture history is preserved), and
     leaves `collection_id` nil.
2. Set the predecessor's state to `migrated`.
3. Return the successor.

Chain accessors: `successor` (`has_one`, foreign key
`migrated_from_id`), `predecessor` (`belongs_to migrated_from`),
`carried_count` — the number of predecessors behind this entry (walk
the chain; at journal scale a loop is correct and honest). The unique
index makes a second migration of the same entry impossible even in a
race; the model raises `LifecycleError` first in the normal path.

**Glyph derivation** — the notation is data, so the model owns it.
`Entry#glyph` returns:

| Entry | Glyph |
|---|---|
| task open **or struck** | `•` (striking is rendered by the view as strikethrough text; the bullet stays) |
| task done | `x` |
| task migrated, successor has `occurs_on` | `<` (it went to the Future Log) |
| task migrated, successor has none | `>` (it went to a month or collection) |
| event | `○` |
| note | `–` |

Priority (`*`) is not part of `glyph`; it stays a separate boolean the
view renders as the signifier column.

## Capture: parser → row

One class method bridges slice 1.1 to persistence:

```ruby
Entry.capture!(line, user:, today:, default_kind: :task, collection: nil)
# => saved Entry, or nil when the parser returns nil
```

Mapping from `Bujo::RapidLog::Parsed`: `kind`, `state` (as the parser
gave it — `:open`/`:done` for tasks, nil otherwise), `text`,
`priority`, `tags`, `occurs_on` ← `date`, `time_of_day` ← `time`,
`logged_on` ← `today`, plus `user` and optional `collection`.
`ArgumentError` from a bad `default_kind` propagates untouched. The
raw line is not stored in v1 — `render` can always reconstruct a
canonical line, and sync (phase 2) transports fields, not raw text.

## Ruled scenarios

Port these into model tests verbatim; `today` is Mon **2026-08-24**,
the user is the `one` fixture.

1. `capture!("call the vet friday +home")` → task, open, text "call
   the vet", `logged_on` 2026-08-24, `occurs_on` 2026-08-28, tags
   `["home"]`. It appears in `daily_log(2026-08-24)` and in
   `monthly_calendar` for August; not in `daily_log(2026-08-25)`.
2. `capture!("x paid the invoice")` → done task; in the daily log,
   not in `open_tasks`.
3. `capture!("   ")` → nil, nothing persisted.
4. A task `migrate_to!(logged_on: 2026-09-01)`: predecessor state
   `migrated`, glyph `>`; successor open, in September's
   `monthly_tasks`, `carried_count` 1; migrating the successor again
   makes `carried_count` 2 on the final entry. The predecessor cannot
   be migrated a second time (`LifecycleError`), and a duplicate
   successor inserted around the model is stopped by the unique index.
5. A task with `occurs_on` migrated via `migrate_to!` → successor has
   nil `occurs_on`/`time_of_day`.
6. `schedule_to!(occurs_on: 2026-10-01)`: predecessor glyph `<`;
   successor appears in `future_log(after: 2026-08-31)`.
7. `complete!` on an event, a note, a done task, and a migrated task
   each raise `LifecycleError`; `reopen!` on a struck task returns it
   to open.
8. A soft-deleted entry disappears from every log scope; its id and
   row survive (`deleted_at` set, `kept` excludes it).
9. Nesting: `capture!` deliberately takes no `parent:` — the caller
   assigns `parent` on the returned entry (that is how 1.3's UI will
   nest a note under the selected task). A child note does not appear
   in `daily_log` directly (roots only); it is reachable through the
   parent's `children`, ordered by `created_at`.
10. Collection name uniqueness: creating "Camping Trip" twice for one
    user fails; soft-deleting the first, then recreating, succeeds; a
    second user may reuse the name (build the second user directly).
11. Fixtures round-trip: an entry fixture with an explicit UUIDv7 id
    keeps that id; a model created without one gets a fresh UUIDv7
    (36 chars, version nibble 7).

## Quality bars for this slice

Everything in the project article, with these rulings:

- **Mutation stays scoped to `Bujo::RapidLog*`** and must remain
  1105/1105. ActiveRecord models are hostile mutation subjects
  (dynamic methods, DB round-trips); the model layer's bar is the
  test suite + coverage + CRAP, not mutant. Do not widen
  `.mutant.yml`.
- `COVERAGE=1 bin/rails test && crap4rb --lcov coverage/lcov.info
  app/ lib/` — the CRAP bar now genuinely covers `app/`.
- **Acceptance evidence for this slice = the model suite (the ruled
  scenarios) plus the existing system lane staying green** (`bin/rails
  test:system`, unchanged). No new browser flow exists to test — a
  model slice has no UI; its absence is not a finding. (Ruled here so
  qa pass 1 does not stall.)
- Fixtures over factories, real DB, no mocking — nothing in this
  slice needs a double.
- File scope: `app/models/`, `db/migrate/` + `db/schema.rb`, `test/`,
  and nothing else. No Gemfile changes (no gems needed), no PLAN.md.

## Non-goals (report, don't add)

Controllers, views, routes, or UI of any kind; writing `hlc` or
`server_seq` (columns exist, nothing touches them); tag normalization
tables; search; Packwerk; recurrence; editing-text operations on the
chain; cascading anything on delete; index/Collection pages. The
migration *ritual* flow (choosing what to do with each open task) is
slice 1.5 — this slice only provides the operations it will call.
