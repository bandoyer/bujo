# Slice 1.5.2a — the Index is the Custom Collection register

Status: **proposed source-alignment correction; implementation not started.**

This amendment corrects one digital translation in landed slices 1.5.2 and
1.5.3b. It does not redesign Collections, add search, or begin another method
spine feature. It makes the existing Custom Collection and Index pages match
Ryder Carroll's relationship between them: the Index is where non-Daily
Collections are recorded so they can be found again.

Authority is `docs/METHOD.md`, then `PLAN.md`, `ARCHITECTURE.md`, this
amendment, and the historical landed contracts. Where this amendment names an
explicit supersession, it wins over the corresponding 1.5.2 and 1.5.3b text.
All unrelated clauses in those landed contracts remain binding.

The source check returned to *The Bullet Journal Method* sections “The Index”
and “Set Up Your Bullet Journal.” The book describes the Index as the
container for the notebook's Collections except the Daily Log and repeatedly
directs the reader to record a Custom Collection's Topic and pages there. It
also says not to index an empty paper Collection. The book does not define a
deliberately hidden, active Custom Collection, an unindex/re-register ritual,
or an exact-name recovery screen.

The web app persists a named Collection before it has entries. Dan's
2026-08-28 ruling is the smallest digital translation of the source: submitting
**Create** is the deliberate commitment, so creation and Index registration
are one atomic operation. A newly created empty page is therefore immediately
reachable from the Index. It never disappears merely because the reader
returns through the fixed Index tab.

## Acceptance contract

- Every kept Custom Collection belongs to its owner's Index. The Daily Log is
  still the explicit book exception; core Today, Month, and Future navigation
  still never becomes Custom Collection rows.
- Successful Custom Collection creation allocates its permanent manual Index
  position in the same transaction. A successful response can never leave a
  kept Collection with `index_position: NULL`.
- The Index lists every kept same-user Custom Collection in server-allocated
  append order. It is not alphabetical, activity-ranked, searched, suggested,
  or generated from Entry text.
- Rename, capture, correction, movement, lifecycle actions, opening, and
  browser refresh never change a Collection's Index position.
- There is no normal unindex, re-register, Add to Index, Remove from Index, or
  Open by Topic gesture. Their routes are removed; crafted requests write
  nothing.
- Existing kept Collections created under the landed unindexed behavior are
  registered once by the migration defined below. No kept page or resident
  Entry is lost.
- Stable UUID Collection URLs and browser history remain valid. Missing,
  malformed, foreign, and soft-deleted ids retain the uniform tenant-safe 404.
- Collection deletion remains limited to a never-used Collection and remains
  soft deletion without cascades. Entry deletion remains deferred.
- UUIDv7, same-user ownership, immutable Entry residency, append-only
  movement, the unique successor chain, exact NULL event/note state, and
  dormant `hlc`/`server_seq` behavior remain unchanged.

## Persistence and one-time transition

Keep the existing nullable `collections.index_position` bigint and its unique
partial per-user index. Do not introduce an Index table, membership table,
boolean, join row, or client-authored rank.

Add one irreversible data-and-constraint migration after
`20260825210000_add_index_position_to_collections.rb`.

### Backfill

For each user independently:

1. preserve every existing non-NULL position exactly;
2. find the greatest position retained by any of that user's kept or
   soft-deleted Collections, or zero when none exists;
3. select only kept Collections whose position is NULL, ordered by
   `created_at ASC, id ASC`;
4. assign consecutive positions after that retained maximum.

The backfill includes empty kept Collections. They are real pages already
created by the old application and must become intentionally reachable under
the corrected rule. Soft-deleted NULL rows remain NULL. A soft-deleted row
that already retains a position keeps it, and its rank is never reused.

The migration writes only `index_position`. It does not touch `updated_at`,
`deleted_at`, `hlc`, `server_seq`, Collection names or ids, or any Entry row.
It must not instantiate the current application model or run callbacks. The
down direction raises `ActiveRecord::IrreversibleMigration`, because the old
unindexed intent cannot be reconstructed after registration.

### Live-row constraint

Add a database check equivalent to:

```sql
deleted_at IS NOT NULL OR index_position IS NOT NULL
```

The existing positive-or-NULL check and kept-row unique partial index remain.
Together they permit a tombstone to retain or omit a position while preventing
the corrected application from persisting another hidden live Collection.

The model mirrors that rule. Raw `index_position` assignment and mass
assignment remain forbidden. The position changes only inside the named
server-owned creation path and the one-time migration.

## Collection creation and ordering

Replace create-then-register with one model-owned operation, named according
to normal Rails style, that:

- accepts the signed-in user, Topic, and an optional caller-supplied UUIDv7 id
  through the already-approved creation boundary;
- normalizes and validates Topic exactly as landed;
- allocates one more than the greatest retained non-NULL position across that
  user's kept and soft-deleted rows;
- saves the Collection and position atomically; and
- retries a bounded uniqueness race so concurrent creates either receive two
  distinct append positions or return a normal validation/refusal response,
  never a raw `RecordNotUnique` page.

Blank and duplicate Topics create no row and consume no durable rank. Request
parameters never supply the rank. Rename preserves it. Soft deletion preserves
it on the tombstone. Positions are not compacted, reused, dragged, moved,
unindexed, or re-registered.

This is **manual append order**, not automatic content sorting: the reader
chooses when to create each Topic, and the Index records those commitments in
that order. The software does not infer a Collection from captured words or
move a Collection because it became active.

## Index and Collection pages

### Index

The Index remains a query over `Current.user.collections.kept`, ordered by
`index_position ASC, id ASC`. Under the live-row constraint that relation is
the complete kept Custom Collection set.

- The first visible text and first heading remain `Index`; `Your collections`
  remains directly underneath.
- The explicit 44px **New Collection** control and the landed trailing blank
  canvas open the same Topic form.
- Successful Create redirects to the canonical Collection page with the
  existing `Collection created.` success notice. Returning through Index shows
  the new Topic immediately.
- Blank or duplicate refusal keeps the Index and open form, preserves the
  submitted Topic, and allocates no row or position.
- `Nothing indexed yet.` appears only when the user has no kept Custom
  Collections. There is no hidden set behind that message.
- Remove the Open by Topic disclosure, form, copy, controller action, and
  route. Do not replace it with search, filtering, recents, suggestions, or an
  all-entry finder in this correction.

### Collection

- The Topic remains the first visible text and first heading.
- The context becomes exactly `Collection`; indexed/not-indexed status is
  redundant and is not rendered.
- Empty copy is exactly `Nothing logged yet.` It contains no instruction to
  add the page to the Index.
- The landed empty-message and trailing-canvas capture behavior remains, with
  Task, Event, and Note choices.
- Remove Add to Index, Remove from Index, their registration wrapper when it
  has no other purpose, and any registration-dependent spacing.
- Manage still contains Rename and the existing guarded Delete Collection
  gesture. No Collection entry or Collection deletion scope changes here.

Success notices continue through the shared flash component and keep their
landed semantic notice styling; they are never rendered as fields or editable
controls.

## Removed commands and crafted-request behavior

The corrected route surface is:

- `GET /index` — complete kept Custom Collection Index;
- `POST /collections` — atomic create plus append registration;
- `GET /collections/:id` — one kept same-user Collection;
- `PATCH /collections/:id` — rename without position change;
- `DELETE /collections/:id` — existing guarded soft deletion; and
- the landed Entry capture, correction, lifecycle, scheduling, and inbound
  movement commands.

Remove:

- `POST /collections/locate`;
- `POST /collections/:id/register`; and
- `DELETE /collections/:id/registration`.

Requests to those removed verb/path pairs receive the application's normal
route-level 404 and perform no read-dependent disclosure or write. Alternate
verbs do not route. Do not leave compatibility actions that clear or allocate
positions behind an absent button.

The Collection transition matrix becomes:

| Request | Success destination | Refusal or miss | Position result |
|---|---|---|---|
| Create valid unique Topic | canonical new Collection | — | next retained rank, atomically |
| Create blank/duplicate Topic | — | Index, open form, 422 | no row and no rank consumed |
| Rename valid unique Topic | same Collection | — | unchanged |
| Rename blank/duplicate Topic | — | same Collection, open Manage, 422 | unchanged |
| Delete never-used Collection | Index | — | retained on tombstone |
| Delete used Collection | — | same Collection with refusal | unchanged |
| Removed locate/register/unindex path | — | route-level 404 | unchanged |
| Missing/foreign/deleted Collection id | — | uniform Collection 404 | no write |

Every relation begins from the current user's Collections. A foreign Topic or
id cannot influence allocation, ordering, response copy, or page content.

## Entry capture and movement remain append-only

This amendment does not change the complete Entry command matrix from landed
1.5.2/1.5.3b/1.5.4.

- Collection capture still uses `Entry.capture!` with exact Collection
  residency and same-user validation.
- Eligible Daily and Monthly residents still use the deliberate Move to
  Collection operation and its exact same-user Topic lookup.
- Monthly Migration may still move an outgoing task to a known exact Topic.
- Moving into, capturing on, or editing within a Collection never writes its
  Index position; the destination already belongs to the Index.
- A missing, deleted, or foreign movement destination still refuses on the
  persisted source page with no successor or predecessor mutation.

Removing **Open by Topic** from the Index does not silently turn either
movement form into broad search or a picker. Destination-selection polish is
outside this correction.

## Sync-sensitive fields

`index_position` remains part of Collection snapshots. Active sync is still
deferred, but the phase-2 intent changes now so the schema does not encode a
feature the product has rejected:

- clients push Collection creation intent with id and Topic, never a rank;
- Rails allocates the authoritative append position while applying creation;
- rename and soft delete preserve that position;
- there are no future register/unregister operations; and
- `hlc` and `server_seq` remain dormant in this slice and are not written by
  the backfill or normal web creation.

The TUI continues to mirror Collection rows. The Index remains a view over
those rows, not a synced entity of its own.

## Ruled browser flows

1. A first-time reader sees `Nothing indexed yet.`, opens New Collection from
   either landed reveal gesture, creates `Camping Trip`, and lands on its empty
   page. Returning to Index immediately shows `Camping Trip`.
2. Creating `Reading List` appends it after `Camping Trip`. Renaming either
   Topic preserves both positions across reload.
3. Capturing Task/Event/Note on a newly created empty Collection changes no
   position. Inbound movement and Monthly Migration destination movement also
   leave order unchanged.
4. The Index and Collection page contain no Open by Topic, Add to Index,
   Remove from Index, or indexed/not-indexed copy. Direct requests to all
   removed routes return 404 and leave exact Collection snapshots unchanged.
5. Empty/duplicate create and rename refusals return to the ruled form/page,
   preserve reader input where landed behavior allows, and create no position
   gap through a partial row.
6. A never-used Collection can still be soft-deleted; a used Collection still
   refuses. The tombstone retains its position, the old URL becomes the
   uniform 404, and a later new Collection receives a new greater position.
7. Migration from the landed schema registers every kept NULL-position row in
   deterministic per-user order without changing existing ranks, tombstones,
   Entries, timestamps, or dormant sync fields.
8. Cross-tenant Index, show, create, rename, delete, removed-route, capture,
   and movement probes reveal no foreign Topic or content and change no
   foreign row.
9. Empty/populated/created/missing/deleted states pass at 390px and 320px in
   both themes and at least two hands: no overflow, tab collision, clipped
   Topic, false input-like notice, or sub-44px control.

## Approval boundary

The source and Dan's ruling settle the primary product behavior: a live Custom
Collection is not deliberately hidden outside the Index. Four necessary
digital translations are proposed here for explicit review:

1. web Create and Index registration are one atomic commitment even before a
   first resident exists;
2. existing kept unindexed rows are appended once in deterministic
   `created_at, id` order after every retained rank;
3. Index order becomes immutable append order—rename preserves it and the
   rejected unindex/re-register workaround disappears; and
4. `index_position` remains nullable for tombstones/wire compatibility while a
   database check forbids NULL on a kept Collection.

Approval of this amendment and `mockups/IndexSourceCorrection.dc.html`
authorizes commit/push of the planning baseline and a stopped-to-started
`six-cg` implementation swarm. Passing QA remains terminal only for the
isolated candidate. Root integration, push of implementation, deployment, and
production repair still require their normal later approvals.
