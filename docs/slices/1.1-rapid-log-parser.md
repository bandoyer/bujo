You are implementing `Bujo::RapidLog`, the plain-text grammar at the
heart of bujo. Every client — the Hotwire PWA now, the TUI later —
captures entries as one line of text; this parser turns that line into
structure. It is the most-load-bearing code in the app and gets the
strictest bars (mutation testing starts here).

Read `PLAN.md` and the Notes in
`swarmforge/constitution/articles/project.prompt` first. **This spec
pre-makes every grammar decision. Where behavior seems debatable, the
tables below are the ruling — do not re-litigate, and put anything you
believe is missing in your final report instead of inventing it.**

## Shape

Pure Ruby under `lib/`, zero Rails dependencies (stdlib `Date` only —
no ActiveSupport, no I/O, no clock access):

```
lib/bujo/rapid_log.rb            # module + public API
lib/bujo/rapid_log/...           # internal decomposition (your call, within the bars)
test/lib/bujo/rapid_log/...      # Minitest, table-driven
```

Public API — exactly this, nothing more:

```ruby
Bujo::RapidLog.parse(line, today:, default_kind: :task) # => Parsed or nil
Bujo::RapidLog.render(parsed)                           # => String (canonical form)

Bujo::RapidLog::Parsed = Data.define(
  :kind,      # :task | :event | :note
  :state,     # tasks: :open | :done · events/notes: nil
  :priority,  # true | false
  :text,      # cleaned text, stripped of prefix and end-zone tokens
  :date,      # Date or nil
  :time,      # "HH:MM" 24-hour String, or nil
  :tags,      # array of downcased tag strings, in order of appearance
  :raw        # the original line, untouched
)
```

- `today:` is required. The parser NEVER reads the clock, the zone, or
  `ENV` — relative dates resolve against the argument. (The reviewer
  greps `lib/bujo/` for `Date.today|Time\.|DateTime|ENV` — any hit is a
  finding.)
- `parse` returns `nil` for blank lines and for lines whose cleaned
  text ends up empty (a date or glyph with no words is not an entry).
- `parse` never raises on any input string. Garbage in → a plain entry
  with the garbage as text.
- Input normalization, in order:
  `line.to_s.dup.force_encoding(Encoding::UTF_8).scrub` (forcing
  first matters: `scrub` is a no-op on a BINARY string, whose bytes
  would then blow up the UTF-8 regexes — encoding is part of the
  never-raise guarantee; `dup` so the caller's string is never
  mutated), then leading/trailing whitespace is stripped before any
  matching, so `"  x Email Sarah"` is a done task. `raw` is the
  scrubbed line with its whitespace intact.
- `default_kind` is what the UI's bullet toggle selects; a glyph in the
  line overrides it. It must be `:task`, `:event`, or `:note` —
  anything else raises `ArgumentError`. (API misuse is a programmer
  error; the never-raise guarantee covers line *content* only.)

## The grammar

```
line   := [prefix] text [end-zone]
prefix := signifier ws glyph ws | signifier ws | glyph ws
signifier := "*"
glyph  := "•" | "." | "x" | "X"     → task ("x"/"X": state :done)
        | "○" | "o" | "O"           → event
        | "–" | "-"                 → note
```

Prefix rules, exactly:

- A glyph counts only when followed by whitespace: `x Email Sarah` is a
  done task; `xylophone practice` is a plain task about xylophones.
  Same for `.`/`-`/`o`: `.gitignore is neat` has no glyph.
- The signifier comes before the glyph or alone (`* • Ship it`,
  `* Ship it`); a `*` anywhere else is ordinary text.
- One glyph max — after the first, everything is text (`x o meeting`
  is a done task whose text is "o meeting").
- No glyph → `default_kind`, state `:open` if task.
- `>` and `<` are NOT capture glyphs — migration and scheduling are
  lifecycle actions, not things you rapid-log. Lines starting with them
  are plain text.

### The end zone

Trailing tokens are consumed from the right, in this order, single
pass each:

1. **tags** — zero or more trailing tokens fully matching
   `+[A-Za-z0-9_-]+` (stored downcased, without `+`; the final array
   is de-duplicated keeping first-occurrence order, so
   `+Home +home` yields `["home"]`)
2. **time** — one token: `H:MM`/`HH:MM` (hour 0–23 in one or two
   digits, minutes always exactly two, so `9:30` parses and `9:5`
   stays text) or `H[:MM]am|pm` (case-insensitive, no space before
   am/pm). Normalized to zero-padded 24-hour `"HH:MM"` (`9:30` →
   `"09:30"`).
3. **date** — longest match first:
   - `YYYY-MM-DD` — absolute; past dates allowed; must be a real
     calendar date (`2026-02-30` stays in the text)
   - `<month> <day>` — month full name or 3-letter, day 1–31;
     resolves to the smallest year ≥ today's year in which the date
     both exists and is ≥ today. For ordinary dates that is the
     familiar "this year, or next year if passed"; for `feb 29` said
     on 2026-08-24 it means **2028-02-29**. A day that exists in no
     year (`feb 30`) stays in the text.
   - weekday, full name or 3-letter — nearest occurrence ≥ today (so
     "friday" said on a Friday means today)
   - `today` | `tomorrow`
4. **tags** again (so `call vet +home tomorrow` and
   `call vet tomorrow +home` both work)

All matching is case-insensitive. What doesn't match stays in the
text — an invalid calendar date (`party feb 30`), a time that isn't
trailing (`14:00 sep 9` keeps "14:00" in text), a mid-text `+word`
that never becomes trailing. Predictability beats cleverness: yes,
`buy the book about tomorrow` parses a date; the UI previews the parse
before saving, and the raw line is always kept.

Deliberately NOT in v1 (report, don't add): `!` signifier, `next
<weekday>`, numeric `9/14` dates, years on month-day, "tonight",
durations, recurrence, timezone handling, escape syntax, i18n.

## render

`render(parsed)` produces the canonical line:

```
[* ][glyph ]text[ +tag]*[ YYYY-MM-DD][ HH:MM]
```

Canonical glyphs, always emitted: `•` open task, `x` done task, `○`
event, `–` note. Dates always render ISO so rendering is stable
regardless of `today`. Tags keep their original order.

**Round-trip property (test it):** for every `parsed` produced by
`parse`, `parse(render(parsed), today: anything)` equals `parsed`
except `raw`. This holds because rendered dates are ISO.

string parsing without raising; `default_kind: :bogus` raising
`ArgumentError`. Also (review findings 2026-08-24): zero-padded time
components whose digits are invalid octal — `09:30` → `"09:30"` and
`14:08`/`14:09` — because string-capture `format("%02d", "09")`
coerces through `Integer()` and raises (convert captures with
`Integer(x, 10)` before formatting); and an ASCII-8BIT/BINARY-encoded
byte string parsing without raising (see the normalization ruling).

## Quality bars for this slice

Everything in the project article, plus mutation testing makes its
entrance here:

- Add `mutant-minitest` to the Gemfile (development/test) with a
  `.mutant.yml` scoping subjects to `Bujo::RapidLog*`, integration
  minitest. Every test class declares `cover 'Bujo::RapidLog*'`.
  (mutant 0.16.3 has been confirmed to install and run on this
  machine with no license prompt.)
- Because mutant's matcher treats every constant under
  `Bujo::RapidLog` as a subject, **test classes must be defined
  outside that namespace** (e.g. a top-level `RapidLogParseTest`) or
  they would be mutated themselves.
- Mutant parses subjects with a Ruby 3.3-level parser even on Ruby
  4.0.6, so **everything under `lib/bujo/` must stay parseable as
  Ruby 3.3** — no 3.4+/4.0-only syntax (`it` block parameters and
  friends). The mutation run failing to read a subject is a blocking
  finding, not an excuse to drop the bar.
- Bar: `bundle exec mutant run` with **zero alive mutants**, or each
  survivor listed in the handoff with a precise justification.
- `COVERAGE=1 bin/rails test && crap4rb --lcov coverage/lcov.info lib/`
  must stay ≤ 6 per method — parsers breed branchy methods; decompose
  until the bar passes honestly.
- No new runtime dependencies. No changes outside `lib/bujo/`,
  `test/`, `Gemfile`/lockfile, and `.mutant.yml`. In particular,
  **pack roles do not edit `PLAN.md`** — the operator updates it at
  integration time; that resolves the apparent conflict with the
  project article.

## Acceptance lane (added 2026-08-24, after qa pass 1)

Qa's first pass stopped before verifying anything: the project article
makes `bin/rails test:system` a role bar, and that command dies with
`LoadError: cannot load such file -- test/system`. The lane has never
existed in this repo — the Phase 0 scaffold shipped `capybara` and
`selenium-webdriver` in the Gemfile without the harness they drive.

That is a gap in this specification, not a defect in the delivered
parser: nothing in slice 1.1 asked for the lane, a browser flow cannot
exercise a library anyway, and the coder was right not to invent one.
Building it is the fix rather than carving out an exception — slice 1.3
needs the lane, and `/usr/bin/chromium`, `/usr/bin/google-chrome-stable`
and `/usr/bin/chromedriver` are all installed on this machine.

Add, inside this slice's existing `test/` scope:

- `test/application_system_test_case.rb` — Rails' generated form:
  `ApplicationSystemTestCase < ActionDispatch::SystemTestCase` with
  `driven_by :selenium, using: :headless_chrome, screen_size: [ 1400, 1400 ]`.
- `test/system/sessions_test.rb` — the one end-to-end flow the app has
  today, driven through a real browser against the `one` fixture user
  (`one@example.com` / `password`):

  1. Visiting `/` renders the sign-in form: an email field, a password
     field, and a "Sign in" button.
  2. Signing in with a wrong password lands back on the sign-in page
     showing "Try another email address or password."
  3. Signing in with the right password shows no such alert and leaves
     a `Session` row for that user.

Assertion 3 leans on the session row on purpose. Root is still the
sign-in placeholder and `after_authentication_url` sends a signed-in
visitor straight back to it, so success and failure differ on screen
only by the flash. It gets a real destination in slice 1.3, and this
test grows with it then.

Rulings for qa, so pass 2 does not stall again:

- **The parser's acceptance evidence is the unit suite** — the ruled
  table and the round-trip property. A library slice has no browser
  flow; its absence is not a finding.
- **The system lane must be green and must actually run.** If the
  browser cannot start, that is a blocking finding to report — never a
  skipped or pending test.
- Everything else under Quality bars stands unchanged.

Two things to check while adding it, because they are cheaper to catch
here than in another round trip:

- `bundle exec mutant run` must still pass. Mutant's minitest
  integration requires every `test/**/*_test.rb`, so it will now load
  the system case and Capybara with it; loading must not break the run.
  (The system test declares no `cover` expression, so it is never
  selected as a subject.)
- `bin/rails test` must stay the fast lane — Rails excludes
  `test/system` from it, and it should stay excluded.

Still no changes outside `lib/bujo/`, `test/`, `Gemfile`/lockfile and
`.mutant.yml`: the lane lives entirely under `test/`. Wiring the slow
lane into `bin/ci` touches `config/` and is the operator's call, not
this slice's.
