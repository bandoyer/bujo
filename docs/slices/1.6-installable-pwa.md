# Slice 1.6 - installable PWA and truthful offline boundary

Status: **PROPOSED 2026-08-29 - specification review only. No
implementation, swarm launch, production enablement, or deployment is
authorized.**

This slice makes Bujo installable from a supporting phone browser, removes the
runtime dependency on Google Fonts, and provides one honest offline fallback.
It does **not** make the journal readable or writable offline. The later phone
rapid-log outbox remains phase 5 work, after the sync spine.

The authority order is `docs/METHOD.md` -> `PLAN.md` -> `ARCHITECTURE.md` ->
this contract. Ryder Carroll's *The Bullet Journal Method*, especially Parts II
and III, governs the product translation: capture and migration remain
deliberate acts, nothing is inferred or queued without the reader's knowledge,
and digital convenience must not pretend that ink was recorded when it was
not. Web-platform details follow the current
[web app manifest](https://www.w3.org/TR/appmanifest/),
[installability](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable),
[service-worker registration](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register),
[maskable-icon](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/How_to/Define_app_icons),
and [offline fallback](https://web.dev/articles/offline-fallback-page)
guidance.

The smallest review board is `mockups/PwaInstallOffline.dc.html`. It fixes the
offline page hierarchy and proposes an app-icon direction; it is not a promise
of offline journal screens.

## Why this boundary is the method-faithful one

The method spine through Custom Collections, the Index, Monthly Migration,
Daily Reflection, inspiration, and master/subtask behavior is now usable. PWA
packaging is therefore allowed to make that practice easier to reach without
replacing it with automatic digital behavior.

An offline outbox would be a second persistence path. It would need client-side
Entry identity, durable operation ordering, idempotent replay, conflict rules,
authentication expiry behavior, and explicit feedback about queued versus
accepted ink. `ARCHITECTURE.md` deliberately places that work after the sync
endpoint and TUI. A small service worker cannot honestly approximate it.

The ruling for 1.6 is consequently:

- installability is convenience;
- locally served fonts make the accepted interface self-contained;
- a neutral fallback tells the truth when the server cannot be reached;
- every journal read and write still requires the live Rails system of record;
- no failed action is described as captured, saved, scheduled, migrated, or
  queued.

## Product outcomes

After one successful online visit in a supported secure browser:

1. Bujo exposes a valid install manifest and may be added to the home screen
   through the browser or operating system's normal affordance.
2. The installed app opens at `/`, stays within the Bujo origin, uses standalone
   display when the platform supports it, and follows the normal Rails
   authentication redirect.
3. Every accepted hand face is served from Bujo's own origin. Loading a journal
   page makes no request to Google Fonts or any other font host.
4. Once the service worker has activated, a failed top-level page navigation
   renders the neutral offline page. It never renders an old journal page from
   the service-worker cache.
5. Restoring the network and choosing `Try again` requests the same intended
   page from Rails.

There is no in-app `Install` button, install coach mark, custom prompt, badge,
notification request, update toast, sync indicator, or offline capture UI.
Platform installation remains a browser/OS action.

## Manifest contract

The public manifest is available without a session at `/manifest.json`. It is
valid JSON, uses a manifest-compatible JSON content type, contains no ERB
whitespace or host-specific URL, and has exactly this product contract:

| Member | Value / ruling |
|---|---|
| `id` | `/` - same-origin and stable across paths |
| `name` | `Bujo` |
| `short_name` | `Bujo` |
| `description` | `A deliberate journal for rapid logging, reflection, and migration.` |
| `start_url` | `/` - no tracking or install query parameter |
| `scope` | `/` |
| `display` | `standalone` |
| `theme_color` | `#f6f1e6` |
| `background_color` | `#f6f1e6` |
| ordinary icons | opaque PNGs at 192x192 and 512x512 with purpose `any` |
| maskable icon | a distinct opaque 512x512 PNG with purpose `maskable` |

Do not add `display_override`, screenshots, shortcuts, categories, share
targets, file handlers, protocol handlers, orientation lock, related apps, or
notification metadata. They add no practice value in this slice.

All manifest and icon URLs are root-relative. There is no mention of
`questlog.dev`, `blackcat.dev`, localhost, a Tailscale name, or a tenant.

## Service-worker boundary

The worker is public, same-origin, and registered from the application
JavaScript at the root-scoped `/service-worker` URL:

```javascript
navigator.serviceWorker.register("/service-worker", {
  scope: "/",
  updateViaCache: "none"
})
```

Registration is feature-detected and intentionally quiet. Unsupported
browsers continue as ordinary Rails/Hotwire clients. Registration failure is
reported to the developer console without changing the page, showing a success
notice, or blocking capture. Repeated registration of the same scope is safe.

The worker uses normal lifecycle replacement. It does not call
`skipWaiting()`, force `clients.claim()`, reload an active journal, or tell the
reader that an update is available. A new worker takes control on the next
normal navigation after activation; a failed install leaves the prior worker
intact.

### Cache ownership

The worker owns one versioned cache whose name begins `bujo-offline-`. Its
install step precaches only:

1. the tenant-neutral `/offline.html` response; and
2. the exact local Permanent Marker WOFF2 file used by that response.

Installation fails atomically if either resource cannot be fetched. Activation
deletes only older cache names with the `bujo-offline-` prefix. It never clears
unrelated CacheStorage, browser HTTP cache, IndexedDB, cookies, local storage,
or another application's cache.

The install fetch for both allowlisted resources uses `cache: "reload"` before
writing them to CacheStorage. Production's long-lived public-file HTTP cache
must not let a newly versioned worker preserve an older offline document.

Changing the offline HTML or its font requires a cache-version change. Cache
keys are root-relative same-origin URLs; no deploy hostname enters the worker.

The worker never writes a runtime response to CacheStorage. In particular it
never caches Daily, Monthly, Future, Index, Collection, Reflection, Monthly
Migration, authentication, settings, Turbo, error, or API responses.

### Request matrix

| Request | Worker behavior | Offline result |
|---|---|---|
| same-origin top-level `GET` navigation | fetch from network with browser cache bypassed | cached neutral fallback only when fetch rejects |
| same-origin top-level Turbo Drive page `GET` accepting HTML, with no `Turbo-Frame` header | same network-first rule | neutral fallback only when fetch rejects |
| an HTTP 3xx/4xx/5xx response | return that live response unchanged | never replace it with `Offline` |
| Turbo Frame or Turbo Stream request | do not intercept | native request failure behavior |
| font, CSS, JavaScript, image, icon, manifest, health, or worker request | do not intercept | normal browser/HTTP-cache behavior |
| any `POST`, `PATCH`, `PUT`, or `DELETE` | do not intercept | fails; nothing is queued or acknowledged |
| cross-origin request | do not intercept | native browser behavior |

The HTML test is explicit rather than “all GETs”: a service worker must not
turn a failed asset, frame, stream, health probe, or future JSON sync request
into an HTML document. Network failure means a rejected fetch; an actual Rails
error response is still the truth.

## Offline page

`/offline.html` is a static, public, tenant-neutral document. It contains no
application layout, session-derived state, CSRF token, journal data, current
date, account name, preference controls, tab bar, capture affordance, or remote
resource.

Visible copy and order are exact:

1. page title: `Offline`
2. explanation: `Reconnect to open your journal.`
3. outcome: `Nothing was logged.`
4. one action: `Try again`

The title comes first. `Try again` performs a plain `GET` for the current
attempted URL, so a failed `/monthly/2026-08` visit retries that URL rather
than silently sending the reader to Today. It uses an HTML form/link behavior,
not inline JavaScript.

The page uses inline structural CSS plus the precached local Permanent Marker
face. It follows the operating system's light/dark preference using the
existing light `#f6f1e6` / dark `#16161e` token values. It deliberately does
not read the Rails `theme` or `hand` cookies: a cached public response remains
identical for every user and account. The action is at least 44x44 CSS pixels,
text wraps without clipping, and there is no horizontal scroll at 320 CSS
pixels.

The document title is `Bujo - Offline`. It may include the approved app icon as
a favicon, but that icon is not placed above the visible `Offline` title.

## State and failure matrix

| State | Required result |
|---|---|
| first-ever visit with no network and no installed worker | browser-native failure; Bujo does not claim otherwise |
| first online visit, worker installing | the live Rails page remains usable; no forced refresh |
| install completed, network available | every page and command behaves exactly as before |
| controlled page, later navigation loses network | neutral Offline page with exact copy |
| already-rendered journal when network disappears | visible DOM may remain on screen, but no new read/write promise is made |
| offline task action or capture | native failure; no Entry change, queued op, success flash, optimistic glyph, or fake count change |
| network returns, `Try again` | Rails serves the originally intended URL, including normal sign-in redirect if needed |
| worker update cannot precache its two resources | old active worker remains; partial new cache is not treated as installed |
| `/offline.html` requested directly | same neutral page for signed-in, signed-out, and different users |
| user signs out or switches account on the same origin | CacheStorage contains no prior user's journal HTML or data |
| server returns 401, 404, 422, or 500 while reachable | that response remains visible; no misleading offline screen |

“Offline” means the browser could not reach a response, not “Rails refused the
request” and not “a page is empty.”

## Security, tenancy, and privacy

- Manifest, worker, icons, fonts, and offline fallback are public but contain
  no user or tenant data.
- Journal authorization remains server-side and unchanged. A service worker is
  not an authorization boundary.
- Worker fetches preserve the original credentials, URL, headers, and redirect
  behavior; only browser-cache bypass is added to admitted page requests.
- No authenticated HTML, Turbo payload, form body, CSRF token, session
  response, Entry text, Collection name, or API response enters CacheStorage.
- Cache names and keys contain no user id, email, Collection id, entry id, or
  host-specific secret.
- The content security policy is not weakened. No `unsafe-eval`, remote font
  origin, worker wildcard, or new third-party origin is added.
- Clearing or updating this worker never deletes user records or invokes a
  Rails command.

## Data and method invariants

This is a presentation/delivery slice. It adds no migration and changes no
model, parser, command, or page semantics.

- Entry and Collection IDs remain UUIDv7.
- Entry residency remains immutable; every move remains append-only.
- ownership and every relation remain same-user validated.
- soft deletion remains non-cascading.
- the unique successor chain and master/subtask completion gate remain intact.
- `priority`, `inspiration`, kind/state, parentage, placement, movement links,
  `occurred_on`, `occurs_on`, timestamps, `deleted_at`, `hlc`, and
  `server_seq` are untouched.
- `hlc` and `server_seq` remain dormant; no service-worker event activates
  sync behavior.
- no background sync, periodic sync, push notification, IndexedDB, local Entry
  table, pending-op queue, or client-generated capture is introduced.

## Executable acceptance contract

### Fast and source lanes

Tests prove:

1. unauthenticated `GET /manifest.json` succeeds with the exact manifest
   values, content type, icon purposes, dimensions, and relative URLs;
2. unauthenticated `GET /service-worker` succeeds as JavaScript, is root
   scoped, owns only the named prefix, and contains the ruled request allowlist;
3. `/offline.html` is byte-identical regardless of session and contains the
   exact visible copy in exact order;
4. every application-layout state links one manifest, contains correct icon
   metadata and theme-color behavior, and contains no `fonts.googleapis.com`,
   `fonts.gstatic.com`, remote font URL, or stale PWA TODO;
5. the seven families/ten faces above have local WOFF2 declarations with
   `font-display: swap`, valid signatures, pinned SHA-256 values, and checked-in
   licenses;
6. icon files have the required formats and dimensions, the PNGs are opaque,
   ordinary/maskable bytes differ, and meaningful maskable artwork stays in
   the safe bound;
7. production-shaped Tailwind compilation remains byte-stable and exposes one
   application stylesheet; no Node/package manager or second CSS bundle
   appears;
8. no schema, dependency, model, grammar, journal route, sync field, or
   deployment configuration changes.

Do not make source-string assertions stand in for behavior where a browser can
prove it. Small structural assertions are appropriate for forbidden origins,
asset inventory, licenses, and the narrowly ruled cache/request list.

### Headless-Chrome system lane

The project-mandated Rails system lane is the authoritative browser evidence.
It uses localhost's secure-context exception and real service-worker APIs; it
does not depend on a separate in-app browser backend.

One isolated PWA test unregisters workers and clears this origin's CacheStorage
in setup/teardown, then proves:

1. the browser sees the manifest link, parses its key members, registers the
   root worker, and reaches `navigator.serviceWorker.ready`;
2. after control is established, CacheStorage contains exactly the offline
   document and Permanent Marker font under one `bujo-offline-` cache, with no
   rendered journal URL or text;
3. Chrome network emulation offline plus a native navigation shows the exact
   fallback copy; a Turbo Drive navigation is covered separately if its
   request shape differs;
4. a 390x844 light-system profile and 320px dark-system profile match the
   approved hierarchy, have no horizontal overflow, use the local marker
   stack, and expose a 44px `Try again` target;
5. the fallback has no tab, preference, capture, Entry, Collection, account, or
   stale journal content;
6. an offline non-GET journal action cannot produce a success UI or change the
   database; restoring the network leaves Rails as the sole authority;
7. an actual online 404 and 500 remain 404 and 500 rather than becoming the
   offline page;
8. after network restoration, `Try again` reaches the originally attempted
   path or its normal authentication redirect;
9. light/dark and every hand still render accepted journal pages without a
   Google Fonts request or geometry regression.

The test does not install Chrome extensions, hit Tailscale, contact production,
or claim that headless Chrome tests OS-specific home-screen UI. Installability
is established through the manifest, worker, icons, secure-context, and
standalone contract; the operating system's menu itself remains manual review.

## Non-goals

Report rather than add:

- offline journal reads, cached “last page,” offline capture, a rapid-log
  outbox, queued commands, replay, merge/conflict behavior, Background Sync,
  or IndexedDB;
- API sync, SSE, `server_seq` stamping, HLC activation, TUI work, or device
  auth;
- push notifications, badges, share targets, shortcuts, install prompts, or an
  app update UI;
- authentication changes, magic links, passkeys, password retirement, account
  settings, or sign-out polish;
- journal UX corrections, search, Entry deletion, new notation, yearly
  migration, automatic placement, or automatic Index behavior;
- domain/DNS/certificate changes, Kamal changes, deployment, or production
  data repair;
- Tailwind upgrades, Node, a CSS redesign, new hand choices, or layout polish
  outside the offline fallback.
