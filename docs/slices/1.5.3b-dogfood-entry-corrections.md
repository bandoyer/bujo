# Slice 1.5.3b — dogfood entry corrections

Status: **APPROVED 2026-08-26 — implementation swarm authorized.**

This is a focused correction slice after hands-on phone review of landed slice
1.5.3a. It makes capture, correction, scheduling, lifecycle ink, Monthly
Migration recovery, and newly created Collections behave as the reader expects
from the page already in hand. It does not begin 1.5.4 Daily Reflection.

Authority remains `docs/METHOD.md`, then `PLAN.md`, `ARCHITECTURE.md`, and the
landed slice contracts. The operator's 2026-08-26 phone review is product
evidence where a minimal digital translation needs correction. In particular,
the approved ordinary Monthly capture ruling below deliberately supersedes the
narrower root-kind rows in `docs/METHOD.md`, `PLAN.md`, `ARCHITECTURE.md`, and
slices 1.5.1/1.5.3a. The Monthly Migration setup remains the book-faithful
task-only mental inventory.

## Acceptance contract

- On an empty writable Daily Log, `Nothing logged yet.` and every usable point
  in that empty entry region open the same capture form. The reader does not
  have to discover a separate hit area below the message.
- Ordinary writable Monthly Calendar and Monthly Tasks capture render the same
  visible `•` Task, `○` Event, and `–` Note controls as Daily and Collection
  capture. The server admits exactly the rendered choice.
- Every current kept Entry can be corrected from its ordinary resident page.
  Correction can revise its words and rapid-log metadata without changing its
  stable id, owner, tree position, page residency, movement history, or task
  lifecycle by accident.
- A standalone unresolved Entry may also change among the bullet kinds its
  page admits. A moved Entry may have its current live end corrected, but kind
  changes do not rewrite a movement chain.
- Scheduling a task or event to a later day in the current month deliberately
  moves it to that Monthly Calendar day. A date after the current month moves
  it to the Future Log. Today, past, missing, malformed, and structurally
  ineligible requests refuse without a write.
- The schedule form keeps the native HTML date input so iOS supplies its native
  picker, but presents a visible label, a legible value, and a full-width
  44px-or-larger target in both themes.
- Daily, Monthly, Future, Collection, and ritual rows retain one stable glyph
  and text origin when selected, expanded, editing, completed, struck, moved,
  or offered an Undo. No interaction-state padding shifts a row sideways.
- Completing a task changes its glyph to `x` and nothing else about its ink.
  Moving changes its glyph/destination history and nothing else about its ink.
  Striking keeps normal ink and draws a clearly visible line through the text,
  in the same color and at least 2 CSS px thick; the glyph is not struck.
- Every successful Monthly Migration resolution offers one immediate Undo.
  Strike Undo reopens the same task. Movement Undo appends a compensating
  successor back to the exact source page; it never deletes or mutates history.
- Creating a Collection visibly opens that new Collection and explains its
  deliberate unindexed state. After its first entry, `Add to Index` is an
  obvious next action. Creation and capture never register it automatically.
- Entry deletion is explicitly deferred. This slice adds no Delete control,
  hard delete, soft-delete command, Trash, or cascading removal.
- Tenant scoping, UUIDv7, immutable placement, one-successor enforcement,
  append-only movement, exact task/event/note state, soft deletion without
  cascades, and dormant `hlc`/`server_seq` behavior remain binding.

## Source findings behind the correction

The current implementation explains the reported phone behavior:

1. Daily's empty copy is inside the content-sized entry list while the blank
   capture button begins after it. The words visibly occupy the page but are
   outside the hit target.
2. Monthly Tasks passes only `task` to the shared kind partial, while Calendar
   passes only Task/Event. The controls are behaving exactly as the earlier
   page vocabulary required; this slice changes that approved product rule.
3. No Entry update route or edit command exists. Lifecycle and movement are
   the only current row commands.
4. Schedule always asks `Entry#move_to!` for a Future destination. The domain
   correctly refuses a same-month date, but the controller never chooses the
   Monthly Calendar destination that `docs/METHOD.md` assigns to same-month
   plans.
5. The schedule input is Rails' native `date_field`; CSS compresses it to a
   small maximum width and visually hides its label. No replacement gem is
   needed.
6. `.entry--selected` adds horizontal padding to the Entry wrapper, shifting
   the shared grid when an action strip opens and in ritual review.
7. `.entry--muted` fades done and migrated tasks, and struck text uses the
   warning color with the browser's thin default decoration.
8. Collection creation already succeeds and redirects to the new canonical
   page, but every new Collection is deliberately unindexed and an empty
   Collection is not registrable. Returning to the Index therefore makes a
   successful create look lost unless the reader understood the intermediate
   page state.

These are presentation and orchestration defects plus one explicitly approved
Monthly vocabulary change. They do not justify a new UI framework, editor
model, date-picker dependency, movement table, ritual record, or search index.

## Daily Log — one truthful empty writing surface

On a writable Daily page, the empty message and the trailing canvas are one
capture affordance:

- tapping `Nothing logged yet.`, its containing empty region, or the blank
  canvas below it opens the existing panel and focuses `Rapid log…`;
- the control remains a real keyboard-focusable button with the accessible
  name `Write on this page`, not a click handler on a generic `div`;
- the visible empty copy may sit inside that button or be labelled by it, but
  screen readers encounter the copy once and the DOM contains no nested
  interactive control;
- entry taps, action-strip taps, edit fields, alerts, navigation, preferences,
  and the fixed tabs never bubble into capture;
- a future Daily page remains capture-closed and its empty copy is not a false
  button.

Success/refusal, placement, focus return, and the populated trailing canvas
remain as landed in 1.5.3a.

## Monthly Log — complete capture vocabulary and stable columns

### Ordinary capture

Both ordinary writable Monthly pages render the shared three-choice control:

```text
[ • ] [ ○ ] [ – ]
[ Rapid log…                                      ] [ Log ]
```

- The initial choice is Task. All three controls are 44px circles with the
  existing selected border/color, glyph fallback, `aria-pressed`, hidden
  `default_kind`, focus, and single-panel behavior.
- Calendar capture still derives `page_kind: monthly_calendar`, `page_on`, and
  `occurs_on` from the tapped server-rendered day. A Note is now a valid root
  resident of that exact row.
- Tasks capture still derives `page_kind: monthly_tasks` and the viewed
  `page_on`. Events and Notes are now valid roots there; a date written into
  their rapid-log line is content metadata and does not move them to Calendar.
- Current and past months remain ordinarily writable. Future Monthly pages
  remain closed except for the existing task-only setup admission inside
  Monthly Migration.
- The Monthly Migration fresh-inventory form continues to show and admit only
  Task. Outgoing/Future candidate relations continue to consider only their
  ruled open-task/event sets; new Monthly Notes and Events are not silently
  swept into the ritual.

The model's root-kind authority and view/controller admission must change
together. A crafted unsupported kind can never succeed merely because a view
was stale, and a rendered choice can never be refused by the old allowlist.

### Entry alignment

All ordinary Monthly rows use the shared fixed signifier, glyph, text, and
metadata columns. At 320px and 390px:

- every root text begins at the same x-coordinate regardless of kind/state;
- wrapped continuation lines remain in the text column;
- the glyph and metadata keep their columns when text wraps;
- opening actions or Edit adds no left/right padding to the row grid;
- Calendar's separate day column remains outside the shared Entry columns;
- nested children retain their one intentional indentation;
- migrated, completed, struck, and restored rows keep the same origin.

The same no-shift rule applies to the selected candidate inside Monthly
Migration. Selection may add background, border radius, or outline without
changing content geometry.

## Entry correction — edit the live words, not journal history

### What can be edited

`Edit` opens an inline panel using the shared kind circles and rapid-log form
anatomy. Its one prefilled line contains the Entry's current words and
canonical rapid-log metadata without a leading kind glyph; the selected kind
button supplies the kind. Saving reparses through `Bujo::RapidLog` so capture
and correction do not grow competing tag/date/time grammars.

A successful correction may update only:

- `text`;
- `priority`;
- `tags`;
- `occurs_on`; and
- `time_of_day`.

It may update `kind` only under the ruled kind-change conditions below.
Parser state does not complete, reopen, strike, or migrate an Entry during
Edit; those remain explicit lifecycle commands. An edited done/struck task
retains its state.

The following never change through Edit: `id`, `user_id`, `page_kind`,
`page_on`, `collection_id`, `parent_id`, `migrated_from_id`, `created_at`,
`deleted_at`, `hlc`, and `server_seq`. `updated_at` changes normally. An edit
never creates a successor, indexes a Collection, reparents a child, or moves a
row because an edited date names another day.

Structural validation remains truthful:

- Calendar roots retain a required `occurs_on` inside their resident month;
- Future roots retain a required `occurs_on`; an overdue Future resident may
  correct its date without being automatically carried into the current
  month;
- child entries continue to share their parent's persisted placement;
- blank text or an otherwise invalid parsed result refuses atomically and
  keeps the submitted edit open.

### Kind changes

Kind correction is deliberately narrower than wording correction:

- the Entry must be kept, have no predecessor, have no successor, and be
  unresolved (`open` for a task, NULL state for an event/note);
- the destination kind must be one the persisted page now admits: Daily,
  Monthly Calendar, Monthly Tasks, and Collection admit all three; Future
  admits Task/Event;
- task to Event/Note sets state to exact NULL; Event/Note to Task sets state
  to `open`;
- a done or struck task must first use Reopen; a moved predecessor cannot be
  edited; and the live end of a movement chain may edit words/metadata but
  keeps its inherited kind.

This is the approved compromise: ordinary mistakes are correctable, but Edit
cannot rewrite what was moved or quietly reinterpret settled task history.

### Rendered and crafted command matrix

`Edit` joins the existing command policy rather than bypassing it:

| Persisted current resident | Daily | Monthly Calendar | Monthly Tasks | Future | Collection |
|---|---|---|---|---|---|
| open task, no successor | Edit + existing task actions | same | same | Edit only | Edit + Complete/Strike |
| done/struck task, no successor | Edit + Reopen | same | same | Edit only if such a kept historical row exists | Edit + Reopen |
| live event, no successor | Edit + Schedule/Move to Collection | same | same | Edit only | Edit only |
| live note, no successor | Edit + Move to Collection | same | same | structurally impossible | Edit only |
| any row with a successor | none | none | none | none | none |

`Migrate`, `Schedule`, Move to Collection, Complete, Strike, and Reopen keep
their existing residency and lifecycle rules except for the schedule
destination correction below. The view uses one offered-command list for both
the row toggle and its strip; no plain-looking row hides an unreachable Edit,
and no crafted `PATCH` can edit a history row.

### Returns and refusal

- Save returns to the Entry's canonical persisted resident page: its Daily
  date, Monthly Calendar/Tasks month, Future Log, or kept Collection.
- Cancel is browser-local, writes nothing, restores the normal action choices,
  and leaves focus on the row toggle.
- Blank/invalid text, disallowed kind, locked history, invalid Calendar/Future
  date, stale row, or crafted placement/ownership/history fields leaves the
  Entry byte-for-domain unchanged and returns to that same canonical page with
  the submitted editable line retained where possible and the established
  refusal copy.
- A missing, foreign, or soft-deleted Entry is the existing nondisclosing 404.
  A Collection resident whose Collection is unavailable keeps the existing
  uniform Collection-not-found response.

Every lookup begins from `Current.user.entries.kept`; request parameters never
choose the user, resident Collection, page, parent, predecessor, or return
destination.

## Scheduling — the date chooses the deliberate destination

The normal Entry `Schedule…` gesture remains available only to eligible live
Tasks and Events on Daily and Monthly pages. Its server-derived decision is:

| Submitted ISO date relative to controller `@today` | Result |
|---|---|
| missing, malformed, today, or past | refuse; no successor |
| later in the current month | append successor to that month's Calendar row |
| after the current month | append successor to Future Log |

For a same-month successor, the server supplies
`page_kind: monthly_calendar`, month-boundary `page_on`, and exact
`occurs_on`. For a later successor it supplies `page_kind: future`, NULL
`page_on`, and exact `occurs_on`. The request supplies only the date. Existing
kind, state, same-user, unique-successor, field-copying, and return-page rules
still come from `Entry#move_to!`.

The resulting historical glyph remains derived from the actual successor:
same-month Calendar is `>`; Future is `<`. Successful and refused commands
return to the persisted source page. A crafted `return_to`, `viewed_on`,
`placement`, `page_kind`, or `page_on` cannot alter destination or redirect a
Collection/Future command into eligibility.

### Native date control

Use Rails' existing `date_field`/HTML `input[type=date]`; do not add a date
picker gem or JavaScript calendar. The expanded step renders:

```text
Schedule for
[ selected date / native date field                         ]
[ Schedule ] [ Cancel ]
```

`Schedule for` is a visible label. The field spans the available phone width,
is at least 44px high, uses the current surface/ink/line tokens, displays its
selected value legibly in Safari and headless Chrome, and never collapses to
the current tiny empty pill. Browser hints such as `min` may guide input but
the server remains authoritative.

## Monthly Migration — one safe immediate Undo

Every successful outgoing or Future resolution redirects to its truthful
stage with a compact confirmation immediately before the current candidate or
empty checkpoint:

```text
Moved to September Tasks.                         [Undo]
```

The message reflects the actual action: struck, target Tasks, exact Topic,
Future date, or target Calendar. It uses the normal ink and stable row columns;
it is not a toast over the fixed tab bar. Only the most recent successful
ritual action is offered. Reloading or proceeding may drop the offer; the
journal result itself remains derived and durable.

### Undo matrix

| Most recent ritual result | Undo operation |
|---|---|
| outgoing or due-Future task struck | call the existing reopen transition on that same still-struck task |
| outgoing task moved to target Tasks, Collection, or Future | append from the current successor back to the predecessor's exact source residency |
| due-Future task moved to target Tasks | append from the current successor back to the original Future residency/date |
| due-Future event moved to target Calendar | append from the current successor back to the original Future residency/date/time |

A movement Undo is a compensating movement, not erasure. The original
predecessor and first successor remain history. A new UUIDv7 successor copies
the current live words/priority/tags and restores the original source's exact
`page_kind`, `page_on`, `collection_id`, `occurs_on`, and applicable
`time_of_day`. Task state on the new live end is `open`; event state is exact
NULL. The destination successor becomes moved under the existing glyph rule.

The Undo command is admitted only when all of these remain true inside one
transaction:

- the named row and every linked row are kept and belong to `Current.user`;
- the original row was in the ruled outgoing or due-Future source set for this
  target month and its result matches one of the actions that stage offered;
- a struck task is still struck with no successor, or a movement's first
  successor is still the live unresolved end with no successor of its own;
- the exact source placement remains structurally valid.

If another tab has reopened, completed, struck, edited into an ineligible
shape, moved, or otherwise superseded the result, Undo refuses with
`REFUSAL_ALERT`, writes nothing, and returns to the recomputed canonical ritual
stage. Missing/foreign/deleted ids use the existing nondisclosing migration
item 404. A crafted target month, source page, Topic, destination, or return
parameter never selects what Undo restores.

Undo success returns to the recomputed stage. The restored entry naturally
re-enters the derived candidate set when still unresolved. There is no generic
entry history screen, multi-level undo stack, persisted ritual progress,
session completion flag, cascade, or successor deletion.

## Lifecycle ink and strike treatment

Entry content never fades merely because its task state changed:

- remove the done/migrated faint-color treatment from every ordinary and
  ritual renderer;
- `x`, `<`, `>`, and destination metadata are the complete visual state
  change for completed/moved work;
- struck text keeps `currentColor`, uses a line-through at least 2px thick in
  all shipped hands, and remains readable in paper-light and Tokyo Night-dark;
- selection backgrounds, warning-colored action buttons, and alerts may keep
  their semantic colors; those colors do not leak into the journal text;
- glyphs, signifiers, text, and metadata retain existing contrast and do not
  become disabled-looking after a lifecycle command.

## Collection creation — make the deliberate next step visible

Creation remains deliberately separate from Index registration:

1. `Create` persists one same-user unindexed Collection and redirects to its
   canonical page with `Collection created.`
2. The title is the first page content. Directly underneath, context says
   `Collection · not indexed`; an empty state plainly says `Add a first entry,
   then add it to the Index.`
3. The empty message and trailing canvas open the same Collection rapid-log
   panel, using the shared three kinds. Reveal creates nothing.
4. After the first successful resident is present, the page renders an
   obvious 44px `Add to Index` action without requiring Manage or a return to
   Index. Register remains a separate explicit POST and keeps server-allocated
   manual ordering.
5. Leaving before capture keeps the unindexed Collection reachable only by
   its stable URL or exact `Open by Topic`; the Index never lists it, suggests
   it, or auto-registers it.

Empty-name, duplicate-name, foreign, missing, deleted, registration, ordering,
rename, unindex, and never-used Collection deletion behavior remain governed
by slice 1.5.2. This slice does not change Collection deletion scope; its entry
deletion deferral is separate.

## Routes and implementation boundaries

Use normal Rails controllers and the existing fat-model boundary:

- add conventional Entry update/Edit behavior to `EntriesController` and the
  Entry command authorization concern;
- add a model-owned correction operation that accepts a parsed line and
  enforces immutable fields, state conversion, movement locks, root-kind
  admission, and same-user structure;
- change the existing Schedule command's server-derived destination; do not
  add a second scheduling controller;
- add one named Monthly Migration Undo POST handled by
  `MonthlyMigrationsController`, with model-owned compensating movement;
- reuse the shared kind, rapid-log, entry-line, action-strip, theme, lettering,
  and flash components rather than copying a Monthly or editor variant;
- update the normal routes only as needed for Entry PATCH and ritual Undo.

No service object, policy-object framework, form-object layer, JavaScript date
picker, editor model, schema migration, dependency, background job, or sync
implementation belongs here.

## State, sync, and security boundaries

- All Entry/Collection reads begin from the signed-in user's kept relations.
- Caller-supplied Entry/Collection UUIDs survive only where creation already
  permits them; every newly appended Undo successor mints UUIDv7 normally.
- `page_kind`, `page_on`, and `collection_id` remain immutable through ordinary
  correction. Movement/Undo always append through an Entry domain operation.
- `migrated_from_id` remains unique; a refused or racing Undo creates no fork.
- Task state remains exactly `open|done|struck|migrated`; Event/Note state is
  exact NULL.
- No write cascades, and all existing soft-deleted rows remain excluded without
  a `default_scope`.
- `hlc` and `server_seq` remain untouched. Edit changes `updated_at` only; the
  active sync slice will later stamp sync fields and retain losing field
  revisions under `ARCHITECTURE.md`.
- Reveal, Cancel, native date selection, kind selection before Save, and an
  offered Undo render are browser-local/read-only. Only explicit submit writes.

## Approval boundary

The operator has already ruled these product questions:

1. ordinary Monthly capture offers Task, Event, and Note consistently;
2. Edit corrects wording/metadata and only narrowly changes kind while page
   residency and movement history stay fixed;
3. same-month Schedule goes to Calendar and later-month Schedule goes Future;
4. the native date picker stays but becomes legible and phone-sized;
5. completion/movement do not fade, strike is thick/current-color, and row

   movement using one compensating append-only successor; and
3. successful Collection creation remains manually unindexed under the landed
