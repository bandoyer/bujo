# Slice 1.5.2 — Custom Collections and the deliberate Index

Status: **operator-approved 2026-08-25; ready for implementation.**

This slice adds the smallest useful Custom Collection page and makes the
disabled Index tab real. It is governed by `docs/METHOD.md`, `PLAN.md`, and
`ARCHITECTURE.md`, in that order, and explicitly supersedes 1.5.1a's temporary
read-only treatment of Collection residents.

The source check for this specification used *The Bullet Journal Method*
sections "Topics and Pagination," "The Index," "Set Up Your Bullet Journal,"
"Migration," and "Custom Collections." The source behavior is deliberately
manual: a Collection begins with a named Topic, a person adds a nonempty
Collection to the Index, and the Index records Collections in the order they
are added. The app keeps the project ruling that Today, Month, and Future have
fixed navigation and are never Index rows. A Custom Collection serves one
specific purpose; the Index remains a map of chosen commitments, not an
inventory generated by software.

## Acceptance contract

- A Custom Collection is one writable residency page. It accepts task, event,
  and note roots through the shared rapid-log grammar and never duplicates an
  entry's residency.
- Creating, naming, renaming, registering, unindexing, opening, and—within the
  narrow rule below—deleting a Collection are deliberate gestures. None happen
  as a side effect of capture, movement, reading, or time passing.
- The Index lists only explicitly registered, kept Custom Collections for the
  signed-in user, in manual registration order. It never lists Daily, Monthly,
  or Future pages and never silently becomes an all-Collections screen.
- An unindexed Collection remains reachable by its stable URL and by an exact
  Topic-name opening gesture. There is no list of unindexed Collections, broad
  search, fuzzy match, prefix match, suggestion, autocomplete, or recent-items
  lens.
- Collection capture continues through `Entry.capture!` with
  `page_kind: "collection"`, NULL `page_on`, and a kept, same-user
  `Collection`. Movement continues only through append-only `Entry#move_to!`.
- Collection tasks gain their normal Complete/Strike/Reopen lifecycle in this
  slice. Every other entry command is admitted or refused by the complete
  matrix below; no controller may infer permission merely from a rendered
  control.
- UUIDv7 ids, exact NULL state for events and notes, immutable entry placement,
  tenant scoping, soft deletion without cascades, the unique successor chain,
  and dormant `hlc`/`server_seq` remain binding.

## Schema — one append-only migration

Add one nullable `bigint` to `collections`:

```text
index_position  bigint, null: true, no default
```

`index_position` carries both explicit registration and its order. NULL means
unindexed. A positive integer means indexed; lower values render first.
Existing Collections backfill as NULL because the app has never recorded a
registration gesture and must not invent one.

Add a unique partial index on `[user_id, index_position]` for kept rows whose
position is not NULL. The model also validates a positive position and
per-user uniqueness among kept rows. Gaps are valid and are never compacted.
There is no `indexed` boolean, alphabetical fallback, or ordering by name,
creation time, update time, or entry activity.

Add a database check that `index_position IS NULL OR index_position > 0`.
Normal creation, assignment, update, and mass assignment may not set or change
the field; they fail loudly and leave the persisted value unchanged. Only the
named register/unindex operations may cross that boundary. Web strong
parameters never admit a raw position, and later sync applies the semantic
operations rather than a client-authored rank.

Registration is one transactional domain operation. It assigns one more than
the greatest non-NULL position currently retained among that user's kept and
soft-deleted Collection rows, or 1 when none exists. The caller cannot submit
a position. Unindexing clears the position. Re-registering appends after every
currently indexed row; it does not recover the old slot. Renaming, capture,
lifecycle changes, and opening a Collection never change its position. Manual
drag/reordering is not part of this slice; unindex then re-register is the only
deliberate way to move a row to the end. Concurrent registrations are
serialized or retried inside the operation; a uniqueness race must become a
normal refusal/retry, never a raw `RecordNotUnique` page.

`index_position` is sync-sensitive even though active sync is not in scope.
Phase 2 snapshots must carry it with the rest of the Collection row.
Register/unregister must arrive as intent-preserving Collection operations;
the Rails authority allocates the position while applying a registration, so
an offline client never wins by supplying an arbitrary rank. HLC resolves
competing registration-state edits on one Collection and `server_seq` orders
the resulting snapshots when those mechanisms become active. This slice does
not write either dormant field and does not add an Index container table.

All existing Collection columns retain their contracts: UUIDv7 string id with
caller-supplied ids preserved, integer `user_id`, `name`, `hlc`, `server_seq`,
`deleted_at`, and timestamps. Entry schema and placement do not change.

The accepted-spec baseline amends `ARCHITECTURE.md` before implementation so

The accompanying prose must say that the Index is a query over kept Custom

## Collection identity and lifecycle

The model calls the reader-facing name a **Topic**, while retaining the
existing `collections.name` column.

- Creation requires a nonblank Topic. Trim leading and trailing whitespace;
  preserve the reader's case and internal whitespace. Kept Topics remain
  case-insensitively unique per user. Do not impose a new arbitrary length or
  character vocabulary in this slice.
- Creation mints or preserves the Collection's UUIDv7 id and always starts
  with `index_position: nil`. Success opens the new Collection; it never checks
  a register box, creates a starter entry, or adds the Collection to the Index.
- Renaming updates that same row and stable UUID URL. It neither moves entries
  nor changes Index registration/order. Blank and same-user duplicate Topics
  are refused with the persisted name unchanged.
- Registration is allowed only for a kept, unindexed Collection that has at
  least one kept associated entry row. A blank rapid-log no-op is not content.
  A repeated registration, an empty Collection, or a deleted Collection is
  refused without allocating a position.
- Unindexing is allowed only for a kept, indexed Collection. It leaves the
  Collection, entries, URL, and name intact. Repeating it is refused.
- Deletion is deliberately narrow: only a Collection that has **never held any
  entry row, kept or soft-deleted**, may be soft-deleted. The check and
  tombstone write are one domain transaction. A Collection with any entry
  history refuses deletion, even if every entry is now soft-deleted; rename or
  unindex it instead. This prevents preserved words and sync ids from being
  stranded behind a deleted page.
- Successful deletion sets only the Collection's `deleted_at`. It does not
  destroy or soft-delete entries, compact Index positions, reuse the id, or
  touch `hlc`/`server_seq`. A deleted Topic may later be reused by a new
  UUID-backed Collection under the existing uniqueness rule.

These operations belong on `Collection` and use a named lifecycle error for
invalid transitions. Controllers translate that error into the same
reader-facing refusal used elsewhere; they do not recreate the rules.

## Residency, reading, and capture

Add a Collection-page root scope that starts from `kept`, requires
`page_kind: "collection"`, the selected `collection_id`, and `parent_id: nil`,
then uses capture order. Children continue to render recursively beneath the
root through `children.kept`. `occurs_on` never grants Collection membership.

`JournalReading` gains the signed-in reader's Collection relation alongside
`user_entries`. Every Index, locate, show, rename, register, unindex, delete,
capture, and destination lookup begins from `Current.user.collections`; routes
that render or mutate a live page add `kept`. No unscoped `Collection.find`
belongs in a controller.

The Collection page's hidden writing surface reuses the Daily Log rapid-log
form and offers task, event, and note kinds. It submits through
`Entry.capture!` with:

```ruby
user:       Current.user
today:      @today
as_of:      @today
page_kind:  "collection"
page_on:    nil
collection: @collection
```

The parser may supply optional `occurs_on` and `time_of_day`; neither becomes
placement. Custom Collections have no temporal admission boundary, but the
server must resolve a kept same-user Collection before calling `capture!`.
Success and refusal both keep the reader on that canonical Collection page.
Capture never registers it automatically. After the first kept entry exists,
the next render exposes the separate Add to Index gesture.

## Deliberate access without discovery

The live Index is a relation over kept rows with non-NULL `index_position`,
ordered by `index_position`, then `id` as a defensive stable tiebreaker. Each
row is one 44px-or-larger link to the canonical UUID Collection route. It shows
the Topic only; entry counts, last-used dates, snippets, tags, and activity
ranking are absent.

The Index also provides **Open by Topic** as a collapsed, explicit form for a
known Collection that may be unindexed. The reader types the complete Topic.
The server trims the query and performs one case-insensitive equality lookup
inside the current user's kept Collections. It returns no candidate list and
does not match substrings, prefixes, tags, or entry text.

- Exact success redirects to the canonical Collection URL whether that
  Collection is indexed or unindexed.
- Blank, missing, renamed-away, deleted, or foreign-only Topics all produce
  the same “No Collection with that exact Topic.” refusal on the Index. No
  record, id, old name, or tenant distinction is disclosed.
- A saved canonical URL and browser history remain valid across rename and
  index/unindex. They return the uniform missing page after allowed deletion.

This exact-name gesture is the minimal digital analogue of deliberately
turning to a known but unindexed page. It is not the deferred broad search and
must not grow suggestions merely because an implementation library makes them
easy.

## Inbound movement belongs in 1.5.2

This specification consciously includes one **Move to Collection…** gesture rather
than deferring all inbound movement to 1.5.3. A writable page alone would leave
Daily notes without the natural destination already promised by
`docs/METHOD.md`, while the monthly ritual reviews unresolved tasks rather
than notes. The gesture is the reusable deliberate movement primitive;
1.5.3 may place the same operation inside its guided task review without
changing its semantics.

An eligible Daily, Monthly Calendar, or Monthly Tasks resident offers Move to
Collection…. Its second step requires the complete Topic of a kept Collection,
using the same exact, case-insensitive, current-user lookup as Open by Topic.
It never renders an all-Collections picker or suggestions.

On success the controller calls the existing operation exactly once with a
resolved model object:

```ruby
entry.move_to!(
  page_kind: "collection",
  page_on: nil,
  collection: destination,
  as_of: @today
)
```

The existing movement contract stands: only an open task or an event/note
with NULL state and no successor can move; the source may be a root or nested
resident, and the successor is a new root with a fresh UUIDv7 id and
`migrated_from_id`; task predecessors become `migrated`; event/note state
remains NULL; priority, tags, text, and user are copied; children do not
follow. Because the destination gesture supplies no `occurs_on`, the
Collection successor clears `occurs_on` and `time_of_day`, as the existing
move-to-a-page-without-a-date contract requires. The predecessor keeps the
historical values.

The predecessor renders `>` and its destination meta names the Collection,
for example `→ Camping Trip`; the existing date destination meta remains
unchanged for Monthly and Future successors. The destination Collection is
not automatically indexed. Success returns to the persisted source page the
reader was reviewing. An unknown, deleted, or foreign destination, a blank
Topic, an ineligible predecessor, or a second move returns to that same source
with `REFUSAL_ALERT` and leaves both sides unchanged.

Future residents remain read-only until 1.5.3. Collection-to-Collection moves
and outbound Collection movement are not introduced here.

## Complete entry-command authorization

Do **not** append `collection` to the current `ACTION_PAGE_KINDS` constant.
`migrate` derives `next_month` from `page_on`, which is correctly NULL on a
Collection, and page-wide admission can no longer express the product rule.

Replace the page-wide allowlist with one command-by-persisted-residency policy
that every member command crosses before its action body. Request parameters
never choose permission or destination:

| Entry command | Daily | Monthly Calendar | Monthly Tasks | Future | Collection |
|---|---:|---:|---:|---:|---:|
| Complete | allow | allow | allow | refuse | allow |
| Reopen | allow | allow | allow | refuse | allow |
| Strike | allow | allow | allow | refuse | allow |
| Migrate to next Monthly Tasks | allow | allow | allow | refuse | refuse |
| Schedule to Future | allow | allow | allow | refuse | refuse |
| Move to Collection | allow | allow | allow | refuse | refuse |

The policy is only the residency gate. `Entry` remains the authority for kind,
state, successor, structural destination, and Future-date validity. The view
renders a control only where both the residency policy and entry lifecycle
allow it.

The complete Collection-resident rendering/command matrix is:

| Persisted Collection resident | Controls rendered | Crafted commands refused |
|---|---|---|
| open task | Complete, Strike | Reopen, Migrate, Schedule, Move to Collection |
| done task | Reopen | Complete, Strike, Migrate, Schedule, Move to Collection |
| struck task | Reopen | Complete, Strike, Migrate, Schedule, Move to Collection |
| migrated task | none | all six |
| event, with or without successor | none | all six |
| note, with or without successor | none | all six |

Complete/Strike/Reopen successes on a Collection resident redirect to that
resident's canonical kept Collection page, derived from the entry's persisted
same-user `collection_id`. Every lifecycle or residency refusal after the
entry is loaded returns to that same page with `REFUSAL_ALERT`, unchanged
state, no successor, and no other row mutation. Crafted `viewed_on`,
`return_to`, `placement`, Collection id, or Topic parameters cannot redirect a
Collection command to a different tenant or make `migrate` reach
`page_on.next_month`.

A foreign, missing, soft-deleted entry or a command whose resident Collection
is foreign/missing/deleted is not a lifecycle refusal: the scoped lookup
renders the uniform 404 state and performs no write. Daily and Monthly command
returns retain their established destinations. Move to Collection success and
refusal return to that persisted source page; they never strand the reader on
the destination as a side effect.

The view's collapsed-strip logic must become command-aware. In particular, a
Daily or Monthly note with no successor now has one action (Move to
Collection…), while the same note on a Collection has none. Existing
Daily/Monthly task and event controls must not disappear.

## Routes and controller boundaries

The route set exposes these reader gestures and no generic search endpoint:

- `GET /index` — deliberate Index;
- `POST /collections` — create an unindexed Collection;
- `POST /collections/locate` — exact-Topic open gesture;
- `GET /collections/:id` — one kept Collection page;
- `PATCH /collections/:id` — rename;
- `POST /collections/:id/register` and
  `DELETE /collections/:id/registration` — explicit index/unindex;
- `DELETE /collections/:id` — guarded soft deletion of a never-used page;
- one new `Entry` member command for Move to Collection.

Names may follow Rails conventions, but the URLs, verbs, and separation of
gestures above are the behavior contract. Keep normal framework controllers:
`CollectionsController` plus the existing `EntriesController`; do not add a
service-object or policy-object layer.

Collection lookup failures use one themed, signed-in 404 page with the title
“Collection not found,” a 44px Back to Index link, and the Index tab active.
Malformed ids, nonexistent ids, another user's id, soft-deleted ids, and a
resident whose Collection is unavailable are visually and semantically
identical. The response is HTTP 404, contains no requested id/Topic or entry
content, and never redirects to another tenant's resource.

Collection form/lifecycle refusals are ordinary reader errors, not 404s:

- create refusal keeps the Index and open New Collection form;
- exact-locate refusal keeps the Index and open exact-Topic form;
- rename, register, unindex, and delete refusal return to the same Collection;
- Collection capture refusal returns to the same Collection;
- every response shows the established alert copy or a concise field error,
  never a 500 or raw exception page.

## Smallest usable phone interface

The existing four-tab shell remains. Index becomes a real link and is active
on the Index, Collection, and Collection-not-found screens. Today, Month, and
Future remain fixed peers; no Collection is promoted into the tab bar.

Page-header order is invariant: the page title is the first visible text and
the first heading in source order. Any descriptor, date, kind, or status sits
directly underneath it; no page places an eyebrow above its title. The current
Daily Log is the one existing exception, so 1.5.2 also reverses its heading and
viewed-date order without changing its wording, navigation, or behavior.
Monthly Log and Future Log already satisfy this rule.

### Index screen

- Header: title `Index` first, context `Your collections` beneath it, and one
  44px-or-larger New Collection button.
- Body: registered Topic links in `index_position` order, each at least 44px
  high. No secondary metadata or automatic sections.
- Empty state: `Nothing indexed yet.` followed by the New Collection gesture.
  It does not show existing unindexed Topics.
- New Collection reveals one labelled Topic field and Create button. Success
  opens the empty unindexed page; refusal preserves the typed value.
- A separate 44px Open by Topic disclosure reveals the exact Topic field and
  Open button. `autocomplete="off"`; there are no results while typing.

### Collection screen

- Header: the Topic as the title first; context `Collection · indexed` or
  `Collection · not indexed` beneath it; one 44px Manage disclosure.
- Body: the resident root trees in capture order, using the shared entry
  partial and collapsed actions ruled above.
- Empty state: `Nothing logged yet.` and `Add a first entry before indexing.`
  The Add to Index control is absent; a crafted register still refuses.
- Writing surface: the existing hidden write-on-page gesture with all three
  kind controls. It remains reachable and 44px-or-larger when the page is
  empty.
- Nonempty/unindexed: one explicit Add to Index action. Indexed: one Remove
  from Index action. Neither is a toggle that changes merely by opening the
  control.
- Manage contains Rename. Delete is rendered only for a never-used Collection
  and requires confirmation; it is absent once any entry row has existed,
  while a crafted delete is still refused.
- Successful rename/register/unindex stays on the Collection. Successful
  deletion returns to Index with confirmation; revisiting the old URL renders
  the uniform 404 screen.

## Ruled browser flows

1. A first-time reader opens the now-live Index tab, sees no automatic
   Collection rows, creates `Camping Trip`, and lands on its empty, unindexed
   page. The empty page refuses registration.
2. The reader captures a task, event, and note directly on that page. They
   appear only there; a reload preserves order; Add to Index appears only after
   content exists.
3. Add to Index returns to the page and the Index then shows `Camping Trip`.
   Creating/contenting/registering `Reading List` appends it. Rename preserves
   order; unindex hides only that row; re-register appends it at the end.
4. An unindexed Collection never appears on the Index. Typing its complete
   Topic in Open by Topic opens it; partial, fuzzy, entry-text,
   deleted, and foreign-only queries all fail identically without candidates.
5. A Collection open task completes and strikes; done/struck tasks reopen.
   The page retains the reader after successes and lifecycle refusals.
   Collection Migrate and Schedule controls are absent and crafted requests
   leave state and successor unchanged.
6. An eligible Daily note uses Move to Collection… with an exact Topic. The
   predecessor shows `>` and the destination Topic; one root successor appears
   in the unindexed Collection, which remains unindexed. The source page is the
   return destination.
7. Eligible Daily and both Monthly resident page kinds can use that same
   gesture. A wrong/foreign/deleted Topic, moved event/note, non-open task,
   Collection resident, and Future resident are refused with no second row or
   predecessor mutation and return according to the matrix.
8. A never-used Collection can be soft-deleted and its old route becomes the
   themed 404. A Collection that has ever held an entry refuses deletion;
   neither kept nor soft-deleted entries are cascaded.
9. Malformed, nonexistent, deleted, and another user's Collection ids render
   the same 404 in Index chrome. Cross-tenant show, capture, rename, register,
   unindex, delete, locate, entry command, and movement-destination probes
   reveal no names or words and change no rows.
10. The populated and empty Index, empty and populated Collection, open action
    strip, exact-name form, and not-found state are exercised at phone width in
    both themes and at least two hand settings. Existing Today, Month, Future,
    capture, lifecycle, and tab flows remain green.

## Approval boundary — genuinely digital decisions

The book settles manual registration, append order, Topic naming, no empty
Index rows, and migration into Custom Collections. It does not prescribe these
five digital translations. The operator approved the following translations
