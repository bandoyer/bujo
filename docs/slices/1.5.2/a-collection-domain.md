# 1.5.2a — Collection domain: Topic, registration, guarded deletion

Task name: `collection-domain`

Derived from the operator-approved `docs/slices/1.5.2-custom-collections-and-index.md`.
That document is the authority; this one only chooses the order in which its
fixed behavior lands. Where the two disagree, the accepted spec wins and the
disagreement is a defect in this file. `docs/METHOD.md`, `PLAN.md`, and
`ARCHITECTURE.md` bind ahead of both, in that order. None of the five approved
digital rulings may be reopened here.

## Why this is a slice of its own

`index_position` carries registration, its order, and a sync-sensitive
contract. It is the one schema change in 1.5.2 and the one place a wrong
allocation rule would be expensive to unwind later. It lands first, with its
domain operations, so the web surface in `collection-pages` consumes rules
that are already pinned rather than inventing them alongside a screen.

The domain operations therefore arrive one slice ahead of their only caller.
That is deliberate, not dead code: `collection-pages` is the named consumer
and adds no rule of its own.

## In scope

One migration plus the regenerated `db/schema.rb`,
`app/models/collection.rb`, `app/models/entry.rb` (one new scope), and
`test/`. Nothing else — no route, controller, view, stylesheet, or

## Behavior

### 1. The migration

One new migration adds exactly one column to `collections`:

```text
index_position  bigint, null: true, no default
```

and, in the same migration:

- a unique partial index on `[user_id, index_position]` restricted to rows
  where `deleted_at IS NULL AND index_position IS NOT NULL`;
- a check constraint named for the rule it enforces, asserting
  `index_position IS NULL OR index_position > 0`.

Every existing `collections` row backfills as NULL. The migration writes no
position, because the app has never recorded a registration gesture and must
not invent one. No other column, table, or index changes. `db/schema.rb` is
regenerated by running the migration, never hand-edited.

Worked example — a database holding `camping` before the migration:

| id | name | index_position (before) | index_position (after) |
|---|---|---|---|
| `0198f3b9-…-0001` | `Camping Trip` | column absent | `NULL` |

### 2. Topic normalization

`collections.name` keeps its column name; the reader-facing word for it is
**Topic**. Before validation, a Topic loses leading and trailing whitespace
and keeps its case and internal whitespace exactly.

| submitted Topic | persisted `name` | outcome |
|---|---|---|
| `"  Camping Trip  "` | `Camping Trip` | created |
| `"Reading   List"` | `Reading   List` | created (internal run preserved) |
| `"camping trip"` while `Camping Trip` is kept | — | refused, `name` taken |
| `"   "` | — | refused, `name` blank |
| `"Camping Trip"` while the only `Camping Trip` is soft-deleted | `Camping Trip` | created, new UUID |
| `"Camping Trip"` owned by another user | `Camping Trip` | created |

No new length limit and no new character vocabulary. The existing
kept-scoped, case-insensitive, per-user uniqueness validation stands.

### 3. Creation is always unindexed

A new Collection mints a UUIDv7 id, or preserves a caller-supplied id, and
persists `index_position` as NULL. Creation never allocates a position,
never writes a starter entry, and never touches `hlc` or `server_seq`.

### 4. `index_position` is writable only by the named operations

Ordinary creation, attribute assignment, `update`, and mass assignment may
not set or change `index_position`. Such a write fails loudly — the record is
invalid with a `:readonly`-shaped error on `index_position` — and the
persisted value is unchanged after `reload`. This mirrors the existing
`Entry#placement_is_immutable` guard, which is the house idiom for a column
the domain owns.

| attempt | result | persisted value |
|---|---|---|
| `Collection.create!(name: "X", index_position: 3)` | raises `RecordInvalid` | no row |
| `collection.update!(index_position: 7)` | raises `RecordInvalid` | unchanged |
| `collection.assign_attributes(index_position: 7); collection.save` | `false` | unchanged |
| `collection.update!(name: "Renamed")` | succeeds | unchanged |
| `collection.soft_delete!` | succeeds | unchanged |
| `register!` / `unindex!` | succeeds | allocated / NULL |

### 5. Registration

`register!` is one transactional domain operation on `Collection`. It is
allowed only when all three hold:

1. the Collection is kept;
2. its `index_position` is NULL;
3. it has at least one kept associated entry row.

It then persists one more than the greatest non-NULL `index_position` among
that user's Collections **counting kept and soft-deleted rows alike**, or `1`
when that user has none. The caller cannot submit a position.

A query predicate answers the same three conditions the operation enforces,
so a screen's affordance and the guard behind it are one rule rather than two
kept in step by hand — the same relationship `Entry.capture_admitted?` already
has with `Entry.capture!`. Name it for what it answers, e.g. `registrable?`.

Any disallowed registration raises `Collection::LifecycleError`, allocates no
position, and leaves every row unchanged. A blank rapid-log line captures
nothing, so a Collection that only ever received blank submissions is empty
and refuses registration.

A uniqueness race is serialized or retried inside the operation. An
`ActiveRecord::RecordNotUnique` must never escape it; a race that cannot be
resolved becomes `Collection::LifecycleError` like any other refusal.

Worked example, one user, in order:

| step | operation | result |
|---|---|---|
| 1 | create `Camping Trip` | `index_position` NULL |
| 2 | `register!` on empty `Camping Trip` | `LifecycleError`, still NULL |
| 3 | capture one entry, `register!` | `index_position` = 1 |
| 4 | create + fill `Reading List`, `register!` | `index_position` = 2 |
| 5 | `register!` `Camping Trip` again | `LifecycleError`, still 1 |
| 6 | `unindex!` `Camping Trip` | NULL; `Reading List` still 2 |
| 7 | `unindex!` `Camping Trip` again | `LifecycleError`, still NULL |
| 8 | `register!` `Camping Trip` | `index_position` = 3, not 1 |
| 9 | `unindex!` `Reading List` | NULL; `Camping Trip` stays 3 |
| 10 | create + fill `Packing`, `register!` | `index_position` = 4, not 1 |

Gaps are valid and are never compacted. Renaming, capture, lifecycle changes,
and reading never change a position.

**The soft-deleted half of the allocation rule is deliberately defensive.**
Registration needs a kept entry and deletion needs zero entry rows ever, so no
gesture in this slice can produce a soft-deleted Collection holding a position.
The accepted spec still requires the allocator to count those rows, because a
phase-2 pull can deliver exactly that row from another device and a position
must never be handed out twice. Implement the rule as written. Test it by
writing such a row directly — `update_column` or raw SQL, past the domain
guard — and labelling the test for what it simulates: a state only sync can
create. Do not relax the deletion or registration guards to make it reachable.

### 6. Unindexing

`unindex!` is allowed only for a kept Collection whose `index_position` is not
NULL. It clears the position and changes nothing else — not the Topic, not the
entries, not `hlc`/`server_seq`. Repeating it raises
`Collection::LifecycleError`.

### 7. Guarded deletion

Only a Collection that has **never held any entry row, kept or soft-deleted**,
may be soft-deleted. The eligibility check and the tombstone write happen in
one transaction. A Collection with any entry history refuses deletion even
when every one of its entries is now soft-deleted.

A matching predicate answers the same question for a caller that needs to know
before asking, e.g. `deletable?`.

| Collection | entry rows | delete |
|---|---|---|
| kept, never captured to | none | succeeds: sets only `deleted_at` |
| kept | one kept entry | `LifecycleError` |
| kept | one soft-deleted entry, zero kept | `LifecycleError` |
| already soft-deleted | none | `LifecycleError` |

Success sets only the Collection's `deleted_at`. It does not destroy or
soft-delete entries, does not compact positions, does not clear
`index_position`, does not reuse the id, and does not touch `hlc` or
`server_seq`. Afterwards the Topic is free for a new UUID-backed Collection
under the existing uniqueness rule.

`SoftDeletable#soft_delete!` stays generic and untouched. The guarded
operation is the only deletion path any `app/` code may call; `collection-pages`
will call it and nothing else.

### 8. `Collection::LifecycleError`

A named error class on `Collection`, mirroring `Entry::LifecycleError`, raised
by `register!`, `unindex!`, and guarded deletion for every invalid transition.
Controllers translate it later; the model never formats reader-facing copy.

### 9. The Index relation

A scope returning that user's registered Topics: kept rows with a non-NULL
`index_position`, ordered by `index_position` and then `id` as a defensive
stable tiebreaker. It never falls back to name, `created_at`, `updated_at`, or
entry activity, and it never lists unindexed rows.

### 10. Exact-Topic lookup

A scope that narrows a Collection relation to rows whose Topic equals a
supplied string, compared case-insensitively after the supplied string is
trimmed. It is equality only — no `LIKE`, no wildcard, no prefix, no
substring, no similarity, and no ordering by relevance. It returns a relation;
choosing the tenant and kept scoping is the caller's job.

| stored Topic | query | matches |
|---|---|---|
| `Camping Trip` | `"camping trip"` | yes |
| `Camping Trip` | `"  Camping Trip  "` | yes |
| `Camping Trip` | `"Camping"` | no |
| `Camping Trip` | `"Camping Trip 2"` | no |
| `Camping Trip` | `""` | no |

### 11. The Collection-page root scope

`Entry` gains one scope returning the root residents of one Collection page:
kept rows with `page_kind: "collection"`, the supplied `collection_id`, and
`parent_id: nil`, in capture order (`created_at`, then `id`). `occurs_on`
never grants membership; a Collection resident carrying `occurs_on` is
included by residency alone, and an entry on another page carrying the same
date is not included at all. Children keep rendering through `children.kept`
and are not roots.

## Invariants this slice must not disturb

UUIDv7 ids with caller-supplied ids preserved; `user_id` tenant scoping on
every query; append-only movement through `Entry#move_to!`; soft deletion
without cascades; immutable entry placement; the unique successor chain; and
dormant `hlc`/`server_seq`, which this slice never writes.

## Required tests — fast lane only

Fixtures and real database rows. Fixed dates or `travel_to`. No doubles for
Rails, the clock, or Active Record. Explicit order assertions.

Migration proof, in the style of `test/models/page_residency_migration_test.rb`:

- forward from the current schema: the column is nullable with no default, and
  every pre-existing row reads NULL;
- forward from a fresh database: the same end state;
- the check constraint rejects `0` and a negative position and accepts NULL;
- the partial unique index rejects a duplicate `[user_id, index_position]`
  among kept rows, and permits the duplicate once one of the two rows is
  soft-deleted, and permits two kept NULL positions for one user.

Model tests:

- Topic trimming, preserved case and internal whitespace, blank refusal,
  kept case-insensitive per-user uniqueness, reuse after soft deletion, reuse
  by another user;
- UUIDv7 generation and caller-supplied id preservation (already covered —
  keep it green);
- creation always persists NULL `index_position`;
- every row of the raw-write table in §4, each asserting the persisted value
  after `reload`;
- the full ten-step registration walk in §5, asserting positions after each
  step and the absence of compaction;
- allocation counts a soft-deleted row's retained position, set up as §5
  describes and named for the sync state it simulates;
- the registration predicate agrees with the operation for empty, nonempty,
  already-indexed, and soft-deleted Collections;
- `unindex!` clears only the position; repeating it refuses;
- every row of the deletion table in §7, asserting Collection-only tombstoning
  and that entry rows — kept and soft-deleted — are untouched and still
  associated;
- refusals raise `Collection::LifecycleError` specifically, not a bare
  `StandardError` or `RecordInvalid`;
- the Index relation's order, its exclusion of unindexed and soft-deleted
  rows, and its tenant boundary. The `id` tiebreaker is defensive and
  unreachable through behavior — the partial unique index forbids two kept
  rows sharing a position — so pin it by asserting the relation's ORDER BY
  names both `index_position` and `id`, and say in the test why a behavioral
  assertion is impossible. Do not fabricate a behavioral one;
- every row of the exact-Topic table in §10, plus the tenant boundary and the
  absence of any prefix/substring match;
- the Collection root scope: kept roots only, correct Collection, correct
  user, capture order with an `id` tiebreaker on identical `created_at`,
  children excluded from roots and reachable through `children.kept`, and no
  `occurs_on` leakage in either direction.
