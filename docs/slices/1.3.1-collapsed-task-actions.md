# Slice 1.3.1 — collapsed task actions (tap to reveal)

A mini slice. The Daily Log's five always-visible task-action controls
(Complete, Strike, Migrate, date field, Schedule) take away from the
journal's minimalism. They collapse behind a row tap, per the mock the
operator picked: the "Tap to reveal" artboard on the
[Collapsed Task Actions canvas](https://claude.ai/code/artifact/016d3b48-d915-416c-a073-14ed1abcb7f6).

**This spec pre-decides the judgment calls; report gaps instead of
inventing rulings.** Behavior of the actions themselves does not
change — same endpoints, same params, same redirects. This is views,
CSS, and one Stimulus controller.

## The interaction (match the mock's three states)

1. **At rest** a task row is pure journal: signifier, glyph, text,
   meta. No buttons, no affordance chrome. Event and note rows are not
   tappable and never show a strip. Migrated task rows are also not
   tappable (they have no actions today; that stays).
2. **Tapping a task row** toggles a compact action strip directly
   beneath it, inside the same row container:
   - open task: Complete · Strike · Migrate · Schedule…
   - done or struck task: Reopen
   The tapped row gets a subtle selected treatment per the mock:
   surface-tinted background, `0.5rem` radius, the row's bottom border
   suppressed while open.
3. **"Schedule…" swaps the strip content** for the date step: the
   date input, a Schedule submit, and an `×` cancel that returns to
   the action strip. Submitting posts the existing `schedule` endpoint
   unchanged (server-side refusal behavior from 1.3 stands).

## Rulings

- **One row open at a time.** Opening a row's strip closes any other
  open strip. The tap is a focus gesture; the page stays calm.
- **Reveal state is client-only.** It is never persisted or sent to
  the server. After an action posts and the page re-renders, every
  strip is closed — that is the correct end of the gesture, not a bug.
- **The toggle is a real `<button type="button">`** carrying
  `aria-expanded` and `aria-controls` pointing at the strip, so
  keyboard and screen-reader use work for free. The coder picks the
  exact markup (the button may wrap the row line), but the actions
  inside the strip remain plain `button_to`/`form_with` forms exactly
  as today — the reveal is the only JavaScript.
- **Strips are server-rendered and hidden**, shown by the Stimulus
  controller (`hidden` attribute or a class it manages). No
  Turbo-Stream round trip to open a menu.
- **Token discipline binds.** The selected-row tint is built from
  tokens (e.g. `color-mix` over `var(--surface)`), never a literal
  color — the mock's rgba value is the *light-theme rendering*, not a
  constant. No color may be defined only inside a media/data-theme
  block. Both themes must stay legible with the row selected.
- **Hit targets stay ≥ 44px** for the row toggle and every strip
  control, per the 1.3 rule.

**No changes** to `app/controllers/`, `app/models/`, `config/`,

## Tests (the system lane carries this slice)

Grow `test/system/daily_log_test.rb`; the browser-lane rules from 1.3
bind (relative assertions, no literal dates, entries created through
the UI).

1. A captured task row shows no action buttons at rest.
2. Tapping the row reveals the strip; tapping again hides it.
3. Opening a second row's strip closes the first.
4. Complete/reopen, strike, and migrate still work through the strip
   (the existing flows 4–6 update to tap the row first — keep their
   assertions).
5. Schedule…: the date step appears, `×` returns to the strip, and
   scheduling through it still produces the `<` predecessor.
6. An event row offers no strip when tapped.
7. A done task's strip offers Reopen (and only Reopen).

Fast lane: only what view changes break (fixture-rendered
markup assertions in the controller tests may need their selectors
updated — updating them is in scope; weakening them is not).

## Non-goals (report, don't add)

Swipe gestures; long-press; animation beyond simple show/hide;
persisting open state; changing action copy, endpoints, or params;
touching the rapid-log bar or any other screen region; the glyph-tap
or ellipsis directions from the unchosen artboards.

### Ruling: the toggle wraps the row line, never the row

`_entry` nests child entries inside the same `<article>` as the row it
draws, and each child renders its own toggle and its own strip of
`button_to` forms. A toggle that wrapped the whole row container would
therefore put buttons inside a button — invalid HTML, and browsers
recover by breaking the outer control, so the parent's own toggle stops
working. The toggle wraps the row line and nothing else: not the strip,
not the children region.

For the same reason the strip renders **between the line and the
children region**, where `_task_actions` already sits. "Directly
beneath the row" means beneath its line, not after its descendants.

### Ruling: a strip always opens on its actions

Reveal state is client-only and one row is open at a time, so a strip
left in the date step gets closed when another row opens or when the
page re-renders. Reopening it shows the **action strip**, never the
date step it was last in. The date step is reachable only by pressing
"Schedule…" in the current gesture; it is never a state a strip opens
into. `×` returns to the action strip without closing the row.

### Ruling: "Schedule…" and "Schedule" must be tellable apart

The reveal control and the date step's submit sit in the same row and
their names overlap. Capybara matches substrings by default, so once
both exist `click_button "Schedule"` matches the strip's "Schedule…"
*and* the submit, and the test dies on an ambiguous match rather than a
real failure. The two keep distinct accessible names — the mock's
ellipsis on the reveal control is the difference — and the system tests
select exactly rather than by substring. Renaming either control to
dodge the collision is a change to action copy, which is a non-goal.

### Ruling: every action needs its own tap

Each action posts and the page re-renders, which closes every strip —
ruled above as the correct end of the gesture. So a flow that acts
twice on a row taps twice. Flow 4 taps to Complete, then taps the
re-rendered row again to Reopen; flow 6 taps before Schedule… and taps
again before Migrate. A test written as one tap followed by two actions
fails on the second, and the fix is the extra tap, never leaving a strip
open across a request.
